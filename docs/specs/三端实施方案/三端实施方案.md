# 旅游规划智能体 · 三端最终实现实施方案

> 版本：v1（2026-11-10）
> 适用：软件工程课程设计最终交付
> 基线：现有 `backend`（Express + TypeScript）、`frontend`（React + Vite）、`database`（MySQL 8，34 张表）
> 目标：C 端用户 App（Android Studio / Kotlin）、B 端旅行社 Web（Java）、平台方 Web（Java）

---

## 0. 决策摘要（先看这一页）

### 0.1 我替你定的默认路线

| 决策项 | 结论 | 理由 |
|---|---|---|
| Node 后端去留 | **保留，作为唯一业务 API** | `/v1` 下 18+ 接口、统一包络、幂等键 + HMAC 防重放、`route_stock` 锁位与过期回收、Casbin RBAC 已成型并有测试；推倒重来等于把已验证资产清零 |
| Java 的角色 | **Spring Boot 承载 B 端 + 平台方 Web（服务端渲染 + BFF 转发）** | 符合「另外两个用 Java」；浏览器侧不碰 JWT，安全边界清晰；工作量可控 |
| C 端 | **Kotlin 原生 App（AS + XML + ViewBinding）**，直连 Node `/v1` | 满足原生要求；现有 React 版作为 UI 与交互参照，不当作交付物 |
| 权限真相源 | **只在 Node**（`sys_role / sys_permission / sys_user_role / sys_role_permission` + Casbin） | Java 只消费 `/users/me/permissions` 下发的 menus/buttons，不复制一套权限模型，避免双写不一致 |
| 数据库 | **34 张表不动，Node 是唯一写入方**；Java 不直连业务表 | 事务边界、库存一致性、幂等语义都锚在 Node，拆开写会立刻出现超卖与重复锁位 |
| 「前后端分离」的落点 | 浏览器 ↔ Java（SSR）、Java ↔ Node（REST），**分离发生在服务之间** | 若必须浏览器侧也分离，见 §15 的 B 方案（Vue3 切换成本） |

### 0.2 三个可切换点（你不认可时改这里，不用重写全文）

1. **想让 Java 全面接管后端**：见 §15「升级路径」，额外增加 3~4 周，需要重写 18 个接口 + Casbin→Spring Security ACL + 库存事务 + 幂等/签名中间件 + 全部测试。
2. **想让 B 端/平台方也走浏览器侧前后端分离**：把 §10 的 Thymeleaf 控制器换成 REST 控制器，前端换 Vue3 + Element Plus，Java 侧多约 1 周（主要是两套页面与联调）。
3. **C 端只想跑核心闭环**：按 §14.3 的裁剪优先级表砍到 P0，Android 工期从 2 周压到 5~6 天。

### 0.3 一句话架构

```
Android App ─┐
             ├─► Node/Express  /v1  （业务 API：认证、生成、行程、订单、库存、RBAC）
Java Web ────┘         │
(B端 + 平台方,          └─► MySQL 8（34 张表，唯一写者 = Node）
 Thymeleaf + BFF)
```

## 2. 三端职责与服务边界

| 端 | 用户 | 核心场景 | 主要接口 |
|---|---|---|---|
| C 端 App | 游客 `TOURIST` | 登录 → 一句话生成 → 多轮调整 → 行程查看/重排/导出 → 线路预订 → 收藏探索 | `/auth/*`、`/plans/*`、`/routes`、`/routes/{id}/stock`、`/orders/*`、`/spots/*`、`/users/{id}` |
| B 端 Web | 旅行社管理员 `AGENCY_ADMIN` | 本社线路上下架、余位库存查看、订单查询与确认、转化率看板 | `/admin/routes`、`/admin/orders`（新增）、`/admin/analytics`、`/roles`?（无权限）、`/users/me/permissions` |
| 平台方 Web | 超级管理员 `SUPER_ADMIN` | 角色管理、权限资源配置、用户与角色分配、全局线路与订单、看板 | `/roles`、`/roles/{id}/permissions`、`/permissions`、`/admin/users`、`/admin/routes`、`/admin/orders`、`/admin/analytics` |

边界三条铁律：

1. **B 端拿不到 `system:*` 权限**（种子数据里 AGENCY_ADMIN 只授了 `route` + `order` 两棵子树），所以 B 端页面里不出现「角色管理/用户管理/权限配置」入口——这是权限驱动的，不是靠前端藏按钮。
2. **平台方不做 C 端动作**（生成行程、下单），只做运营与治理。
3. **库存只有 Node 能改**：Java 与 Android 都只是「查余位 → 提交订单 → 看返回」，任何「本地算一下还剩几席」的写法都算越权。

## 6. 三端一致性：签名、幂等、刷新（最容易翻车的地方）

现有前端 `frontend/src/lib/http.ts` 已经把这套算法跑通，**Android 与 Java 必须逐字节复刻**，否则后端一律 403。

### 6.1 签名算法（三方同一份）

```
message = HTTP_METHOD \n
          /v1/完整路径（含 query）\n
          X-Timestamp（UTC ISO8601，如 2026-11-10T07:30:00.000Z）\n
          X-Nonce（16~128 位字母数字/中划线，每次请求唯一）\n
          SHA256(请求体原始字节) 的小写十六进制
X-Signature = HMAC-SHA256(key = 当前 Bearer access token, message) 的小写十六进制
时间窗 ±5 分钟；nonce 落库防复用；仅 POST/PUT/PATCH/DELETE 需要
```

### 6.2 三方实现对照

| 语义 | Web 前端（已有） | Android（新写） | Java（新写） |
|---|---|---|---|
| 待签 body | 请求拦截器里先把对象 `JSON.stringify` 成字符串再赋值给 `data` | Interceptor 里 `Buffer` 一次性读取，`ByteString` 重新构造 `RequestBody` | `RestClient` 发送前先 `ObjectMapper` 序列化成 `String`，再 `Content-Type: application/json` 发这个字符串 |
| SHA-256 | `crypto.subtle.digest` | `MessageDigest.getInstance("SHA-256")` | 同 Android |
| HMAC | `crypto.subtle.importKey/sign` | `Mac.getInstance("HmacSHA256")` + `SecretKeySpec` | 同 Android |
| 幂等键 | 每次写请求自动 UUID | 同（同一业务重试要复用同一 key，做在 Repository 层） | 表单提交生成 UUID，放进隐藏域，重试复用 |
| 时间戳 | `new Date().toISOString()` | `DateTimeFormatter.ofPattern("yyyy-MM-dd'T'HH:mm:ss.SSS'Z'").withZone(ZoneOffset.UTC)` | 同 Android |

### 6.3 必须做的一致性测试（否则联调一定卡三天）

1. 在 `backend/src/api/api.test.ts` 里已有的签名样例中取 1 组（方法/路径/时间戳/nonce/body/期望签名），做成三端各一份**固定向量单元测试**：Android `SigningInterceptorTest`、Java `RequestSignerTest`，输入相同输出必须逐字符一致。
2. 同一 body 若被两端序列化出空格差异（`{"a":1}` vs `{"a": 1}`），签名必挂 → 统一 `ObjectMapper` 配置（无缩进、不排序键）。
3. query 参与签名：Android 的 `HttpUrl` 拼参顺序与后端 `originalUrl` 必须一致；统一用「不排序、按添加顺序」并在测试里固定。

### 6.4 401 刷新（Android 关键）

- 用 OkHttp `Authenticator`（不是普通 Interceptor）：它天然保证「一次 401 → 一次重试」，避免死循环。
- 并发 5 个请求同时 401 时，只允许 1 个发 `/auth/refresh`：`Mutex` + 共享 `Deferred<Boolean>`（对应 Web 版的 `renewing` 单飞）。
- refresh 失败 → 清空 `SessionStore` → 发一个 `SessionExpired` 事件 → 导航回登录页（对应 `AuthExpiredError` + `expired` 标志）。
- Java 侧同理：`NodeApiClient` 捕获 20012 时用 session 里的 refresh_token 续期一次，仍失败则 `invalidateSession()` + `redirect:/login?expired`。

## 7. 权限在 Java 侧怎么落地（不重建 RBAC）

### 7.1 数据流

```
管理员登录 Java → NodeApiClient 调 /auth/login/account + /auth/captcha
            → 调 /users/me/permissions 拿 {menus, buttons}
            → 存进 HttpSession：tokens / userId / roles / buttons / menus
            → 页面渲染：菜单遍历 menus，按钮用权限码判断
            → 每次写操作：Java 生成签名转发 Node，Node 用 Casbin 复核（真正的门禁在后端）
```

### 7.2 关键原则

1. **Java 不做第二套权限表**，只缓存 Node 下发的结果；角色被改后重新登录即刷新（也可加一个「刷新权限」按钮调 `/users/me/permissions`）。
2. **前端隐藏 ≠ 后端放行**：Java 侧 `@PreAuthorize` 只是体验优化，真正的 403 由 Node 的 `requireAction` 出（对应 20013 + 固定文案）。
3. 双入口分流：`/agency/**` 要求 `route:line:query` 或 `order:manage:query`；`/platform/**` 要求 `system:*`。`SUPER_ADMIN` 两处都能进，`AGENCY_ADMIN` 进 `/platform` 直接 403 页。

### 7.3 权限码 → 页面/按钮映射（直接抄这张表做 Thymeleaf 判断）

| 页面 | 查看权限 | 按钮 | 按钮权限 |
|---|---|---|---|
| `/agency/routes` 线路库 | `route:line:query` | 发布 / 编辑 / 下架 / 导出 | `route:line:add` / `:update` / `:delete` / `:export` |
| `/agency/orders` 订单 | `order:manage:query` | 确认处理 / 导出 | `order:manage:update` / `:export` |
| `/agency/dashboard` 看板 | `order:manage:query` | — | — |
| `/platform/roles` 角色 | `system:role:query` | 新增/编辑/删除/导出、分配权限 | `system:role:add/update/delete/export` |

## 9. Android 端详细设计

### 9.1 分层

```
ui (Fragment + ViewBinding) 
  → 只调 ViewModel
viewmodel (StateFlow<UiState>) 
  → 只调 Repository
repository (缓存 + 网络编排，持有 Idempotency-Key 复用逻辑)
  → ApiService(Retrofit) + ItineraryCache(Room)
data/remote (Interceptor 链：Auth → Signing → Log)
```

### 9.2 页面清单与交互对齐（参照现有 React 屏）

| Android 屏 | 对应现有组件 | 关键接口 | 要点 |
|---|---|---|---|
| 登录 / 注册 / 找回 | `LoginScreen` `ResetPasswordScreen` | `/auth/*` | 密码/短信双 Tab；图形验证码必须带 `captcha_id`；密码 8–72；失败即换码 |
| 计划首页 | `PlanScreen` | — | 「新建」→ 对话页；「导入行程检查硬伤」→ 对话页预置问句 |
| 智能体对话 | `ChatScreen` | `POST /plans` | 输入「N天/目的地」→ 提交 → 展示语义标签与工具标签气泡 → 跳行程页 |
| 行程详情 | `ItineraryScreen` | `GET/PATCH /plans/{id}` | 按天时间轴、判官认证块、一键重排、导出 |
| 探索 | `ExploreScreen` | `GET /spots` | 先用列表+静态底图承接地基（图钉用相对坐标叠加），地图 SDK 作为可选增强 |
| 我的 | `ProfileScreen` | `GET/PUT /users/{id}` | 手机号脱敏展示、退出登录、管理入口（仅当 `route:line:query` 存在） |
| 预订 | `BookingScreen` | `GET /routes` + `stock` + `POST /orders` | 选线路→查余位→提交；提交前再查一次余位；15 分钟提示 |
| 导出 | `ExportModal` | — | 本地拼 Markdown → 系统分享（`Intent.ACTION_SEND`），比 Web 的复制更实用 |

### 9.3 与 Web 前端的逻辑对应（避免漏功能）

| Web 行为 | Android 对应做法 |
|---|---|
| `App.tsx` 用正则抽「N 天/目的地」 | ViewModel 里同一份正则，抽不到给默认（5 天 / 昆明），并在 UI 上让用户可改 |
| `camel()` 递归转换后端字段 | DTO 直接 `@Json(name="plan_id")` 显式映射，去掉运行时转换 |
| `restoreSession()` 静默续期 | `SessionStore` 有 refresh_token 时，启动时先调一次 `/auth/refresh` |
| `clearSession({expired:true})` 事件 | `SessionStore.expired: Flow<Boolean>`，登录页显示「登录状态已失效」 |

### 9.4 手机端特有的三个坑

1. `minSdk 26` 以上才有 `java.time`，不要再引 ThreeTenABP。
2. 明文 HTTP 只允许 debug：`network_security_config.xml` 放 `res/xml/debug`，release 强制 HTTPS。
3. 模拟器访问本机后端用 `10.0.2.2:3001`，真机用局域网 IP —— 写进 `buildConfigField("String","API_BASE", ...)`，不要硬编码。

## 10. Java Web 详细设计

### 10.1 请求链路

```
Browser --(Session Cookie)--> [Thymeleaf Controller]
                                   └─► NodeApiClient --(Bearer + HMAC)--> Node /v1
```

### 10.2 关键类职责

| 类 | 职责 |
|---|---|
| `SecurityConfig` | 表单登录、`/login` 放行、`/agency/**` 与 `/platform/**` 的 URL 级规则、CSRF（Thymeleaf 表单自动带 token） |
| `AdminAuthFilter`（或 `AuthenticationProvider`） | 登录时调 Node `/auth/login/account` + `/auth/captcha`，把 Node 返回的 user/token 包成 `AdminUserDetails` |
| `PermissionService` | 从 session 的 `buttons` 判断 `has(code)`，供 `@PreAuthorize("@perm.has('route:line:add')")` 使用 |
| `SessionTokens` | 保存 access/refresh/expiresAt，写操作前检查是否过期并先续期 |
| `RequestSigner` | §6 的 Java 实现，输入 method/path/body 输出四个头 |
| `NodeApiClient` | 统一 `exchange()`：拼 URL、签名、解析包络、`code!=0` 转 `NodeApiException`、401 走 refresh、403 转页面提示 |
| `NodeApiException` | 携带 `status/code/message/traceId`，Controller 用 `@ControllerAdvice` 统一渲染错误页并展示 traceId（便于和后端日志对账） |

### 10.3 页面清单

**B 端（`/agency`）**
- `dashboard`：今日生成数 + 成单转化率（`/admin/analytics`）
- `routes`：列表（分页/排序白名单）、发布、编辑、下架
- `orders`：本社订单列表、按状态筛选、确认处理、导出 CSV
- `stock`：按 `route_id + travel_date` 查余位（只读）

**平台方（`/platform`）**
- `dashboard`：全局 KPI
- `roles`：列表、新增、编辑、删除（内置角色前端置灰 + 后端 403）、分配权限（权限树多选，全量覆盖语义）
- `permissions`：权限树维护（MENU/BUTTON 两级，BUTTON 必须三段式，前端即校验）
- `users`：用户列表、新建、改角色、禁用/启用
- `routes` / `orders`：全量视角（与 B 端同模板，靠权限与 agency 过滤区分）

### 10.4 交互细节（对齐后端约束）

1. 分页只允许 `page 1~100`、`size 1~100`、排序字段白名单 —— 前端下拉只给白名单项，避免 400。
2. 写操作全部 POST + CSRF token，重复提交由 `Idempotency-Key` 兜底。
3. 错误提示直接透传后端 `message`（如「该日期余位不足」），不要改写成「操作失败」。
4. 删除是逻辑删除（`is_deleted`），页面提示「已下架」而非「已删除」。
5. traceId 显示在错误页角落，答辩时可以现场演示「按 traceId 查日志」。

## 13. 风险与预案

| # | 风险 | 触发表现 | 预案 |
|---|---|---|---|
| 1 | 双后端技术栈被质疑「为什么两套」 | 答辩提问 | 用服务边界图讲：Node=AI 与交易域（无状态、高并发、工具编排），Java=管理域（会话、模板、表单、审计）；共享认证与权限真相源，不是重复建设。若老师坚持统一，走 §15 |
| 2 | 签名三端不一致 | 403 全量出现，且只在写接口 | 固定向量单测（§6.3）；联调第一件事就是跑这三条 |
| 3 | Android 401 风暴 | 5 个请求触发 5 次 refresh，refresh_token 被轮换失效 | `Authenticator` + `Mutex` 单飞；refresh 结果全局缓存到下次成功请求 |
| 4 | Java 会话与 Node 令牌双过期 | 页面能打开但一点就 403 | `SessionTokens` 在每次写前检查 `expiresAt`，提前 2 分钟续期 |
| 5 | 库存超卖 | 并发下单后 `locked+sold > total` | 不自行算余位；DB CHECK 兜底；压测专门做 10 并发抢 3 席 |
| 6 | Thymeleaf 模板与权限码写死 | 改权限后页面不变 | 菜单/按钮一律从 session 的 menus/buttons 渲染，禁止硬编码显示条件 |
| 7 | 时间不够 | S3 做不完 | 按 §14.3 砍 P2，保 P0 |
| 8 | Android 真机连不上后端 | 网络错误 | `BuildConfig.API_BASE` 可配；debug 明文白名单只对开发域名开放 |
