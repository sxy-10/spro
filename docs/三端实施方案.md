# 旅游规划智能体 · 三端最终实现实施方案

> 版本：**v3（2026-11-24）**
> 适用：软件工程课程设计最终交付
> 基线：`backend`（Express + TypeScript）、`frontend`（React 18 + Vite）、`database`（MySQL 8）
> 目标：C 端 Android 原生 App（Kotlin）、B 端旅行社 Web、平台方 Web（Java BFF + React SPA）
>
> **v2 相对 v1 的核心变化**：B 端/平台方由 Thymeleaf 服务端渲染改为**浏览器侧前后端分离 + Java BFF**；
> 浏览器不再持有任何令牌，令牌与 HMAC 签名全部收进 Java 服务端；WebSocket/SSE 改为一次性 ticket 直连；
> 补入本轮课程新增能力（Kafka、定时器、实时推荐、日志审计）在三端中的落点。
>
> **v3 相对 v2 的变化（当日修订）**：SPA 源码从 `frontend/agency-web` 收进 **`java-web/agency-web`**，
> 由 `frontend-maven-plugin` 在 Maven 生命周期内构建、**Spring Boot 同源托管**（后端与前端产物打成一个 jar）；
> 同源后 **CSRF 由「关闭 + 补偿」改为真正启用**（`CookieCsrfTokenRepository` + `X-XSRF-TOKEN`）；
> Nginx 从「SPA 托管方」降级为「生产可选的外层 TLS 反代」。

## 0. 决策摘要（先看这一页）

### 0.1 项目已定路线（不再是可选项）

| 决策项 | 结论 | 理由 |
|---|---|---|
| Node 后端去留 | **保留，作为唯一业务 API 与唯一数据库写入方** | `/v1` 下 18+ 接口、统一包络、幂等键 + HMAC 防重放、`route_stock` 锁位与过期回收、Casbin RBAC 已成型并有测试；推倒重来等于把已验证资产清零 |
| Java 的角色 | **Spring Boot 3.3 承载 B 端 + 平台方的 API 与 BFF**（REST 控制器 + Spring Security 会话），**不做模板渲染** | 满足「另外两个用 Java」；浏览器只拿 JSON，令牌与签名止于服务端；BFF 做页面级聚合，避免前端串行请求 |
| B 端/平台方前端 | **React 18 + Vite + Ant Design SPA**，源码在 **`java-web/agency-web`**，Maven 前端插件构建、**Spring Boot 同源托管**（产物进 jar 内 `static/`），只与同源 `/api` 交互 | 团队已有 React 能力；分离落在「浏览器 ↔ Java」（JSON + 会话）；同源部署零 CORS、Cookie 最省心，仓库形态就是一个 Spring Boot 工程 |
| C 端 | **Kotlin 原生 App（AS + XML + ViewBinding + MVVM + Retrofit）**，直连 Node `/v1` | 满足原生要求；React + Capacitor 版仅作交互参照，**不当作交付物** |
| 权限真相源 | **只在 Node**（`sys_role / sys_permission / sys_user_role / sys_role_permission` + Casbin） | Java 只消费 `/users/me/permissions` 下发的 menus/buttons，不复制权限模型，避免双写不一致 |
| 数据库 | **核心表不动，Node 是唯一写入方**；Java 不直连业务表 | 事务边界、库存一致性、幂等语义都锚在 Node，拆开写会立刻出现超卖与重复锁位 |
| 浏览器侧安全边界 | 浏览器**只持 `HttpOnly` 的 `JSESSIONID` + 仅供 CSRF 的 `XSRF-TOKEN`**（后者可被 JS 读取是设计使然，不含任何凭据）；access/refresh token 与 HMAC 密钥**止于 Java 服务端**；WebSocket / SSE 用 **30 秒一次性 ticket** | 保留 v1「浏览器不碰令牌」的安全意图，同时允许浏览器侧分离 |
| 「前后端分离」的落点 | **浏览器 ↔ Java（REST/JSON + Session）**、**Java ↔ Node（REST + HMAC）**、**Java ↔ Node 内部接口（独立内部密钥）** | 分离发生在浏览器侧；同时用 BFF 把管理面 API 收进内网，浏览器永远碰不到 `/v1/admin/*` |

### 0.2 保留但默认不启用的切换点

1. **让 Java 全面接管后端**：见 §15 升级路径，额外 3~4 周。
2. **退回 Thymeleaf 服务端渲染**：把 §10 的 REST 控制器换回模板控制器、SPA 作废，工期约省 1 周（仅当答辩明确要求 SSR 时启用）。
3. **C 端只跑核心闭环**：按 §14.3 砍到 P0，Android 工期从 2 周压到 5~6 天。

### 0.3 一句话架构

```
Browser (React SPA) ──Cookie: JSESSIONID + XSRF-TOKEN──┐
                                                      ▼
                                    Spring Boot :8080（同一个 jar）
                                     ├─ /                        → SPA 静态产物（classpath:/static）
                                     ├─ /api/**、/login、/logout → @RestController（BFF）
                                     └─ 其它路径                 → index.html（SPA history 回落）
                                                      │
                                       Bearer + HMAC  │  内部密钥
                                                      ▼
Android App (Kotlin) ──直连──────────────────► Node /v1 :3001 ──► MySQL 8 / Redis / Kafka
                                                      ▲
Browser ──一次性 ticket（30s）──────────────────────┘  WebSocket /v1/im/ws、SSE /v1/stream

生产可选形态：外层 Nginx :443 只做 TLS 终止与 gzip，/ 与 /api 原样反代到 :8080（不托管文件、不改路径）
```

### 0.4 差异清单（v1 → v2 → v3，评审逐条对照用）

| 项 | v1 | v2 |
|---|---|---|
| B 端/平台方渲染 | Thymeleaf SSR | React SPA + Java REST（BFF） |
| 浏览器持有的凭据 | 仅 JSESSIONID（SSR 天然） | 仅 JSESSIONID（SPA 显式保证） |
| 前端框架 | 未定 / 切换点写 Vue3 + Element Plus | **React 18 + Vite + Ant Design**（复用现有能力，不引 Vue） |
| 前端工程位置 | `java-web/templates` | `java-web/agency-web`（v3：收进 java-web，Maven 前端插件构建） |
| SPA 托管与端口 | — | v2：Nginx :8088 + `/api` 反代；**v3：Spring Boot :8080 同源托管**，Nginx 仅生产可选 |
| CSRF | 模板表单自动带 token | v2：关闭 + 三条补偿；**v3：启用 `CookieCsrfTokenRepository`（`X-XSRF-TOKEN`）** |
| 长连接鉴权 | 未涉及 | 一次性 ticket，不进 Java 代理 |
| MQ | 秒杀用 Redis Stream | 秒杀改 **Kafka**；IM 保持 Redis Stream（理由见附录 A） |
| 课程新增能力 | 无 | 定时器、实时推荐、日志审计的落点见 §11.6 |

## 2. 三端职责与服务边界

| 端 | 用户 | 核心场景 | 主要接口（经 Java `/api` 转） |
|---|---|---|---|
| C 端 App | 游客 `TOURIST` | 登录 → 一句话生成 → 多轮调整 → 行程查看/重排/导出 → 线路预订 → 收藏探索 | `/auth/*`、`/plans/*`、`/routes`、`/routes/{id}/stock`、`/orders/*`、`/spots/*`、`/users/{id}` |
| B 端 Web | 旅行社管理员 `AGENCY_ADMIN` | 本社线路上下架、余位库存查看、订单查询与确认、转化率看板、客服台、实时大屏 | `/admin/routes`、`/admin/orders`（新增）、`/admin/analytics`、`/users/me/permissions`、`/im/*` |
| 平台方 Web | 超级管理员 `SUPER_ADMIN` | 角色管理、权限资源配置、用户与角色分配、全局线路与订单、看板、**日志审计三页** | `/roles`、`/roles/{id}/permissions`、`/permissions`、`/admin/users`、`/admin/routes`、`/admin/orders`、`/admin/analytics`、`/admin/audit/logs` |

边界铁律（v2 由 3 条扩到 6 条）：

1. **B 端拿不到 `system:*` 权限**（种子数据里 AGENCY_ADMIN 只授 `route` + `order` 两棵子树），所以 B 端页面不出现「角色管理/用户管理/权限配置」入口——权限驱动，不是前端藏按钮。
2. **平台方不做 C 端动作**（生成行程、下单），只做运营与治理。
3. **库存只有 Node 能改**：Java 与 Android 都只是「查余位 → 提交订单 → 看返回」，任何「本地算一下还剩几席」的写法都算越权。
4. **浏览器只能访问 Java**：SPA 与后端同源，业务请求一律走 `/api/*`（由同一个 Spring Boot 进程提供），**不得直连 Node `/v1`**。唯一例外是 WebSocket/SSE，凭 Java 下发的一次性 ticket 连接。
5. **`/v1/admin/*` 只对 Java 开放**：网关按出口 IP 白名单 + Node 侧 `ADMIN_ALLOWED_IPS` 双重校验；C 端 App 或浏览器命中一律 403。
6. **`/internal/*` 永不对外**：Java 不转发该前缀、外层 Nginx（若启用）不得为其配置 location、Node 侧只绑定内网地址；且用**独立内部密钥**签署，不复用用户 token。

> 这 6 条就是答辩时的「服务边界图」：**同一个 Node 服务，C 端业务面对公网，管理面和定时任务面只对内网 BFF 开放**。

### 5.2 新增两个管理接口的契约（同步写入 `docs/specs/API_V1.md`）

```
GET /v1/admin/orders?status=&route_id=&page=&size=
→ data: { list: [{ order_id, route_id, route_title, contact_mobile(masked),
                   people_count, amount, status, travel_date,
                   created_at, expires_at }], total, has_more }
权限：order:manage:query
隔离：AGENCY_ADMIN 仅见本 agency_id 的订单；SUPER_ADMIN 全量

→ data: { order_id, status: 'CONFIRMED' }

语义：仅当 status=CREATED 且未过期可确认；否则 409/20010 或 20015
副作用：写 product_stat_event(type=order_confirmed)，不重复扣库存（库存已在锁位阶段锁定）
```

### 5.3 BFF 聚合接口约定（Java → SPA）

**原则**：一页一请求。聚合接口只做「并行调用 + 字段裁剪 + 组装」，不改变任何业务语义。

```
GET /api/agency/routes-page?page=1&size=20
→ { code:0, trace_id:"...", data:{ list:[], total:120, parts:{
      analytics:{ today_orders:12, conversion:0.18 },
      filter_options:{ route_types:[], status:[] }
   }}}
```

- Java 内部用 `CompletableFuture` 并行调 Node 2~5 个接口，总超时 3s；
- 单个 part 失败**不拖垮整页**：该 part 返回 `null` 并置 `partial:true`，前端显示局部重试；
- 写操作一律不聚合，1:1 转发并透传 `Idempotency-Key`；
- `trace_id` 用 Java 的 `X-Trace-Id` 贯穿（Node 侧日志同源，便于按 traceId 对账）。

### 5.4 WebSocket / SSE 一次性 ticket 契约

```
# 1) 浏览器带会话向 Java 换票
POST /api/realtime/ticket   body:{ purpose:'ws' | 'sse' }
→ data:{ ticket:"7f3c...", expires_in:30,
         url:"ws://127.0.0.1:3001/v1/im/ws?ticket=7f3c..." }

# 2) Java 内部换票（HMAC 调 Node）
POST /v1/im/ws-ticket   body:{ purpose, uid }   ← 校验 ADMIN/TOURIST 身份
→ Node 生成一次性 ticket：Redis SETEX ws:ticket:{ticket} 30 {uid,purpose,used:false}

# 3) 浏览器直连 Node
ws://node/v1/im/ws?ticket=xxx  → 校验存在、未用、未过期 → 立即 DEL（用完即焚）
失败：1008/4001 关闭，SPA 重新换票一次，再失败跳登录
SSE 同理：/v1/stream?ticket=xxx，连接建立后即作废
```

> 为什么不让 Java 反向代理长连接：Spring 代理 WS/SSE 要处理半关闭、心跳、背压，工期风险高；ticket 方案同样能做到「浏览器不持长期令牌」，成本低一个量级。

## 6. 一致性：签名、幂等、刷新（最容易翻车的地方）

**v2 变化：浏览器不再参与签名。** 只剩两份实现必须逐字节一致——**Android（OkHttp Interceptor）与 Java（RequestSigner）**。
`frontend/src/lib/http.ts` 的实现降级为「历史参考」，B 端 SPA 不得再引用。

### 6.1 签名算法（两端同一份）

```
message = HTTP_METHOD \n
          /v1/完整路径（含 query）\n
          X-Timestamp（UTC ISO8601，如 2026-11-10T07:30:00.000Z）\n
          X-Nonce（16~128 位字母数字/中划线，每次请求唯一）\n
          SHA256(请求体原始字节) 的小写十六进制
X-Signature = HMAC-SHA256(key = 当前 Bearer access token, message) 的小写十六进制
时间窗 ±5 分钟；nonce 落库防复用；仅 POST/PUT/PATCH/DELETE 需要
```

### 6.2 两端实现对照

| 语义 | Android（新写） | Java（新写） |
|---|---|---|
| 待签 body | Interceptor 里 `Buffer` 一次性读取，`ByteString` 重新构造 `RequestBody` | `RestClient` 发送前先用 `ObjectMapper` 序列化成 `String`，再 `Content-Type: application/json` 发这个字符串 |
| SHA-256 | `MessageDigest.getInstance("SHA-256")` | 同 Android |
| HMAC | `Mac.getInstance("HmacSHA256")` + `SecretKeySpec` | 同 Android |
| 幂等键 | 同一业务重试复用同一 key，做在 Repository 层 | 表单提交生成 UUID 存 Session，重试复用 |
| 时间戳 | `DateTimeFormatter.ofPattern("yyyy-MM-dd'T'HH:mm:ss.SSS'Z'").withZone(ZoneOffset.UTC)` | 同 Android |

### 6.3 必须做的一致性测试（否则联调一定卡三天）

1. 从 `backend/src/api/api.test.ts` 的签名样例取 1 组（方法/路径/时间戳/nonce/body/期望签名），做成两端各一份**固定向量单测**：`SigningInterceptorTest`（Android）、`RequestSignerTest`（Java），输出必须逐字符一致。
2. 同一 body 若被两端序列化出空格差异（`{"a":1}` vs `{"a": 1}`）签名必挂 → 统一 `ObjectMapper` 配置（无缩进、不排序键）。
3. query 参与签名：Android 的 `HttpUrl` 拼参顺序必须与后端 `originalUrl` 一致，统一「不排序、按添加顺序」并在测试里固定。

### 6.4 401 刷新

- **Android**：用 OkHttp `Authenticator`（不是普通 Interceptor），天然保证「一次 401 → 一次重试」；并发 5 个 401 只允许 1 个发 `/auth/refresh`（`Mutex` + 共享 `Deferred<Boolean>`，对应 Web 版的 `renewing` 单飞）；失败 → 清 `SessionStore` → `SessionExpired` 事件 → 回登录页。
- **Java**：`NodeApiClient` 捕获 `20012` 时用 Session 里的 refresh_token 续期一次，仍失败则 `invalidateSession()`；SPA 收到 401 JSON → 跳 `/login?expired=1`。

### 6.5 浏览器侧红线（写进安全扫描检查项）

1. SPA 代码与产物中不得出现 `X-Signature`、`X-Nonce`、`Authorization: Bearer`；
2. `localStorage` / `sessionStorage` 不得出现任何 token（F12 逐项检查）；
3. 所有跨域请求只允许 `/api`，出现 `/v1/` 直连视为缺陷；
4. 会话 Cookie（`JSESSIONID`）必须 `HttpOnly`，`document.cookie` 读不到；唯一可读 Cookie 是 `XSRF-TOKEN`，**它只能是 CSRF token，绝不能塞 token/uid/角色等任何身份信息**。

## 7. 权限在 Java 与 SPA 侧怎么落地（不重建 RBAC）

### 7.1 数据流

```
浏览器 → Java /api/auth/captcha（代理图片）→ /api/auth/login
       → Java 调 Node /auth/login/account + /auth/captcha
       → Java 调 Node /users/me/permissions 拿 {menus, buttons}
       → 存 HttpSession：tokens / userId / roles / buttons / menus
       → 返回给 SPA：{ user, menus, buttons }（不含任何 token）
SPA    → 路由守卫按 menus 渲染侧边栏；按钮用 <Permission code="xxx"> 包裹
每次写操作 → Java 生成签名转发 Node，Node 用 Casbin 复核（真正的门禁在后端）
```

### 7.2 关键原则

1. **Java 不做第二套权限表**，只缓存 Node 下发的结果；角色被改后重新登录即刷新（也可加「刷新权限」按钮重新拉取）。
2. **前端隐藏 ≠ 后端放行**：SPA 守卫与 Java `@PreAuthorize` 都只是体验优化，真正的 403 由 Node 的 `requireAction` 出（`20013` + 固定文案）。
3. **双入口分流**：`/agency/**` 要求 `route:line:query` 或 `order:manage:query`；`/platform/**` 要求 `system:*`。`SUPER_ADMIN` 两处都能进，`AGENCY_ADMIN` 进 `/platform` 直接被 Java 拦成 403 页。
4. **菜单与按钮一律来自接口**：SPA 里禁止 `role === 'ADMIN'` 这类硬编码判断（现有 `App.tsx` 的旧写法即为反例）。

### 7.3 权限码 → 页面/按钮映射（直接抄这张表做前端路由与按钮判断）

| 页面（SPA 路由） | 查看权限 | 按钮 | 按钮权限 |

| `/agency/routes` 线路库 | `route:line:query` | 发布/编辑/下架/导出 | `route:line:add` / `:update` / `:delete` / `:export` |

## 10. Java BFF 详细设计

### 10.1 请求链路

```
Browser(SPA) ──Cookie: JSESSIONID + XSRF-TOKEN──► Spring MVC @RestController（同进程托管静态与 /api）
                                                        ├─► NodeApiClient ──Bearer+HMAC──► Node /v1
                                                        └─► InternalClient ──内部密钥────► Node /internal/*
Browser ──ticket（30s）──► Node /v1/im/ws、/v1/stream（长连接，不经 Java）
```

### 10.2 关键类职责

| 类 | 职责 |
|---|---|
| `SecurityConfig` | JSON 登录接口、`/api/auth/**` 放行、`/api/agency/**` 与 `/api/platform/**` 的 URL 级规则、`JsonAuthEntryPoint`（401/403 返回 JSON）、**CSRF 启用**（`CookieCsrfTokenRepository`，见 §10.5）、静态资源与 SPA 路由放行 |
| `SpaForwardController` | 把 `/`、`/agency/**`、`/platform/**` 等非 `/api` 路径 forward 到 `index.html`，保证 SPA history 路由刷新不 404（生产不依赖 Nginx `try_files`） |
| `AdminAuthFilter` / `AuthenticationProvider` | 登录时调 Node `/auth/login/account` + `/auth/captcha`，把返回的 user/token 包成 `AdminUserDetails` |
| `PermissionService` | 从 Session 的 `buttons` 判断 `has(code)`，供 `@PreAuthorize("@perm.has('route:line:add')")` 使用 |
| `SessionTokens` | 保存 access/refresh/expiresAt；写操作前检查过期并预续期（提前 2 分钟） |
| `RequestSigner` | §6 的 Java 实现，输入 method/path/body 输出四个头 |
| `NodeApiClient` | 统一 `exchange()`：拼 URL、签名、解析包络、`code!=0` 转 `NodeApiException`、401 走 refresh、403 转语义错误 |
| `InternalClient` | 调 `/internal/timers/*`，用 `INTERNAL_API_KEY` 签独立签名，与用户 token 完全隔离 |
| `WsTicketController` | `/api/realtime/ticket`：校验会话 → 调 Node 换票 → 只回 ticket 与 url |
| `GlobalExceptionHandler` | 统一 JSON 错误体 `{code,message,trace_id}`，透传 Node 文案，不吞成「操作失败」 |

### 10.5 交互约束（对齐后端与浏览器安全）

1. **CSRF 启用**（v3 变更）：`CookieCsrfTokenRepository.withHttpOnlyFalse()`，token 写入 `XSRF-TOKEN` Cookie，SPA 在 `lib/csrf.ts` 读出后放进 `X-XSRF-TOKEN` 头；`/api/auth/login`、`/api/auth/captcha` 放行，其余写请求缺头一律 403。**保留两条纵深防御**：Cookie `SameSite=Lax`、写操作仍带 `Idempotency-Key`。答辩口径：同源部署后没有理由关闭 CSRF，关掉反而是安全缺口。
2. 401/403 一律返回 JSON（`20012`/`20013`），SPA 按 code 跳登录或弹无权，**不要 302 到登录页**（SPA 无法处理重定向）。
3. 分页只允许 `page 1~100`、`size 1~100`、排序字段白名单——前端下拉只给白名单项，避免 400。
4. 错误提示直接透传后端 `message`（如「该日期余位不足」），不要改写成「操作失败」。
5. 删除是逻辑删除（`is_deleted`），页面提示「已下架」而非「已删除」。
6. `X-Trace-Id` 在错误页角落显示，答辩可现场演示「按 traceId 查日志」。
7. **会话超时体验**：SPA 每 5 分钟静默调 `/api/me` 续期一次；连续 2 次 401 才跳登录，避免轮询把用户踢出。
8. **静态资源缓存**：`index.html` 设 `no-cache`（否则前端发版后用户拿到旧壳），`/assets/**` 带 hash 的可长缓存（`max-age=31536000, immutable`）；配置写在 `WebMvcConfig`，不依赖 Nginx。
9. **构建与部署只有一条路径**：`mvn package` → `java -jar`。开发期允许 `npm run dev`，但**验收与答辩一律用 jar**，避免「本地能跑、换台机器白屏」。

## 13. 风险与预案

| # | 风险 | 触发表现 | 预案 |
|---|---|---|---|
| 1 | 双后端被质疑「为什么两套」 | 答辩提问 | 用服务边界图讲：Node=业务与交易域（无状态、高并发、工具编排、唯一写库），Java=管理域 **BFF**（会话、聚合、审计、内网隔离）；共享认证与权限真相源，不是重复建设。若老师坚持统一，走 §15 |
| 2 | 签名两端不一致 | 403 全量出现，且只出现在写接口 | 固定向量单测（§6.3）；联调第一件事就是跑这两条 |
| 3 | SPA 残留浏览器侧令牌 | 安全扫描或 F12 里发现 `web_tokens`、`X-Signature` | `shared-auth` 在 B 端彻底移除依赖；把「无 token、无签名」写成验收项与扫描项 |
| 4 | WS ticket 被重放 | 同一 ticket 建立两条连接 | 一次性 + 30 秒 + 绑定 uid/purpose；服务端用完即 DEL；异常关闭码统一 |
| 5 | **SPA 刷新 404 / Cookie 失效** | 在 `/agency/orders` 按 F5 得到 404；或登录成功刷新即掉登录 | `SpaForwardController` 把非 `/api` 路径回落 `index.html`；Cookie `Path=/`、`SameSite=Lax`；若外层再加 Nginx，只做 TLS 原样转发、不改写路径 |
| 6 | Java 会话与 Node 令牌双过期 | 页面能打开但一点就 403 | `SessionTokens` 每次写前检查 `expiresAt`，提前 2 分钟续期；SPA 5 分钟静默 `/api/me` |
| 7 | 前后端职责写死 | 改权限后页面不变 | 菜单/按钮一律来自 `/api/me`，禁止 `role === 'ADMIN'` 硬编码 |
| 8 | 库存超卖 | 并发下单后 `locked+sold > total` | 不自行算余位；DB CHECK 兜底；压测专门做 10 并发抢 3 席 |
| 9 | Kafka 发送失败 | Lua 扣了库存但订单永不生成 | 发送失败立即回补库存并返回 503；消费端手动提交 offset；重试/死信 topic 可观测 |
| 10 | Flink 环境搭不起来 | 作业起不来，演示空转 | 先用本地 MiniCluster + 造数脚本；Plan B 用 Kafka 消费者窗口聚合，但答辩按 Flink 讲 |
| 11 | 时间不够 | S3 做不完 | 按 §14.3 砍 P2，保 P0；SPA 页面先做「能看能操作」，样式后补 |
| 12 | **CSRF token 未下发导致写接口全 403** | 登录后点保存即 403，错误体为 `Invalid CSRF token` | 首个写请求前先 `GET /api/me` 让 token Cookie 落地；确认 `XSRF-TOKEN` 未被 `HttpOnly` 挡掉；**禁止**用 `csrf().disable()` 临时绕过 |
| 13 | **`mvn package` 在答辩机失败** | 报 `npm: command not found` 或前端构建超时 | `frontend-maven-plugin` 自带 `installNode` 受管 Node，不依赖系统 Node；离线环境用 `-DskipFrontend` 跳过构建并复用已有 `static/`；首次构建提前在目标机器跑一遍 |

### 14.2 验收口径（与现有测试对齐）

| 项 | 判定 |
|---|---|
| 未登录访问受保护接口 | 401 + `code=20012`（JSON，不重定向） |
| 已登录越权 | 403 + `code=20013` + 文案「权限不足，禁止访问」 |
| 密码错 5 次 | 429 + `code=20014` |
| 幂等重试 | 同键同体返回相同结果，`orders` 仅 1 条，锁位不重复 |
| 余位不足 | 409 + `code=20010` + 「该日期余位不足」 |
| 库存约束 | 任何时刻 `locked_seats + sold_seats <= total_seats` |
| 三端数据一致 | 同账号同数据在 App 与 SPA 显示一致 |
| **浏览器无令牌** | F12：localStorage/sessionStorage 无 token；请求头无 `X-Signature`/`Authorization`；Cookie 只有 `JSESSIONID` 与 `XSRF-TOKEN` |
| **CSRF 生效** | 带会话 Cookie 但不带 `X-XSRF-TOKEN` 调 `POST /api/agency/routes` → 403；补上该头 → 正常 |
| **单 jar 可交付** | 清空 `static/` 后 `mvn package`，`java -jar` 启动，`:8080/` 直接出登录页；全程无需 Nginx、无需单独前端进程 |
| **浏览器不能直连 Node** | 直接访问 `http://node:3001/v1/admin/routes` → 403/连接被拒 |
| **内部接口不可达** | 公网访问 `/internal/timers/expire-orders` → 404/连接被拒（写进扫描报告） |
| **ticket 一次性** | 30 秒后失效；同一 ticket 第二次握手被拒（4001/1008） |
| **定时器生效** | 把 cron 临时改为每分钟：超时订单变 CANCELED、库存预热 key 存在、看板数值变化，日志可查 |
| **推荐闭环** | 埋点事件进入 Kafka → Redis 出现 `rec:interest:{uid}` → 探索页展示「为你推荐」 |
| **审计三页** | 系统/操作/登录日志均有数据，可按用户、时间、类型筛选并导出 |
| **MQ 语义** | 关消费者 → consumer lag 上涨；开启 → 自动补单；同一消息重投不重复建单 |

### 14.5 答辩话术（v2 新增，固定口径）

- **为什么 Java 只做 BFF 不写库**：事务与库存一致性锚在 Node，Java 写库会立刻出现超卖与重复锁位；BFF 的职责是会话、聚合、内网隔离。
- **为什么浏览器侧分离还能不碰令牌**：浏览器只持 `HttpOnly` Cookie；token 与 HMAC 密钥在 Java 进程内存里；长连接用 30 秒一次性 ticket。
- **为什么有两套 MQ**：秒杀与埋点的下游是 MySQL 与 Flink，需要削峰、重放、与 Flink 生态对接 → Kafka；IM 离线通知的消费逻辑本身就依赖 Redis（在线状态、离线计数），Stream 是最短路径 → 保留（附录 A）。
- **为什么不用 Vue3**：团队 React 能力已成型（C 端参照版、现有 workbench），换框架是纯学习成本，与交付质量无关。
- **为什么 SPA 放在 `java-web` 里仍算前后端分离**：判据是「浏览器拿的是 HTML 还是 JSON、构建与运行是否解耦」，不是「仓库是否两个」。SPA 是独立工程、独立构建（Maven 前端插件）、独立路由，只通过 `/api` 交互 JSON；同仓只是把交付收敛成一个 jar，省掉跨工程发布与 CORS 配置。
- **为什么 CSRF 打开而不是关掉**：同源部署后不存在跨域障碍，关闭 CSRF 等于自弃一层防护；现在由 `CookieCsrfTokenRepository` + `X-XSRF-TOKEN` 正常生效，写接口缺 token 直接 403。

## 附录 A：IM 离线通知为何不迁 Kafka（决策记录）

| 维度 | 结论 |
|---|---|
| 现状 | `im:notify` 走 Redis Stream（`XREADGROUP` + PEL + 手动 `XACK`），消费端查会话参与者、在线跳过、离线 `INCR im:offline:{uid}` |
| 不迁理由 1 | **消费逻辑强依赖 Redis**：判断在线与写离线计数都是 Redis 操作，迁 Kafka 后仍是「Kafka → 消费者 → Redis」三跳，多加一套依赖却没有减少耦合 |
| 不迁理由 2 | **消息特征不匹配**：低频轻量通知，无削峰、无重放、无多消费者组需求；Kafka 的优势在这里用不上 |
| 不迁理由 3 | **故障语义更简单**：Redis 不可用时整条链路安静降级；迁 Kafka 后会出现「Kafka 在转、Redis 挂着」的部分故障，补偿逻辑要重写 |
| 不迁理由 4 | 老师点名的 Kafka 场景是**秒杀削峰与埋点行为日志**，IM 是课程中自加功能，不在任务清单内 |
| 统一话术 | 「秒杀和埋点用 Kafka，因为要削峰、要和 Flink 对接、要持久重放；IM 离线通知用 Redis Stream，因为消费逻辑依赖 Redis 在线状态、量级轻、要安静降级，少一跳网络。」 |
| 判据 | 迁移的分界线不是「技术栈统一」，而是**消费逻辑的依赖在哪里**：下游是 MySQL/Flink → Kafka；下游就是 Redis 本身 → Stream 最优 |
