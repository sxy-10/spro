### 第 1 幕：认证与授权是两层（预期输出）

```
━━ 第 1 幕：认证（你是谁）与授权（你能干什么）是两层 ━━
  ✓ 无 token 查角色列表（未登录）                 HTTP 401 / 业务码 20012
  ✓ 游客 token 查角色列表（无权限）                HTTP 403 / 业务码 20013
  ✓ 超管 token 查角色列表（放行）                 HTTP 200 / 业务码 0
```

**讲解词**：401 是组员1 的认证层拦的——"你没登录，我不知道你是谁"；403 是我的
授权层拦的——"我知道你是谁，但你没这个权限"。401 和 403 不能混用，这是接口
契约（API_V1.md）里写死的。

### 第 2 幕：改完权限立即生效（预期输出）

```
━━ 第 2 幕：改完权限立即生效（无需重启 / 不用等缓存过期）━━
  ✓ 初始：社管无权查角色列表                       HTTP 403 / 业务码 20013
  超管给社管补上 system:role:query（id=104）→ 社管授权 12 → 13 条
  ✓ 补上后社管立即能查（200）                     HTTP 200 / 业务码 0
  ✓ 摘掉后社管立即查不了（403）                    HTTP 403 / 业务码 20013
  ✓ 摘掉后恰好等于原始授权，数据已还原，不留痕
```

**讲解词**：引擎策略有 30 秒缓存（防止每个请求都查库）。为什么改完权限不用等
30 秒？因为每个写接口成功后有一个钩子主动把缓存作废——下一个请求自动重读
数据库。服务端日志能佐证：`rbac.policy.invalidated` → `rbac.policy.loaded`。

## 三、讲解要点（配合演示说）

1. **为什么不用 `if (role === 'ADMIN')`**：3 角色 × 35 权限 = 105 个格子，全部存在
   数据库 47 行勾选记录里。加新角色 = 插几行数据，代码 0 行改动。
2. **为什么用 Casbin**：判定入口唯一。路由上写一行
   `requireAction('system:role', 'query')` 就完成拦截，业务代码零侵入。
3. **fail-closed**：策略库挂了 → 退回登录时的权限快照；两者都没有 → 拒绝。
   安全系统宁可临时不可用，绝不放行。
4. **403 不告诉用户缺什么权限码**：那等于给攻击者画地图。缺失信息只写进
   服务端 `rbac.denied` 日志。
