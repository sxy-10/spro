### 0.3 先弄懂 5 个名词（后面全是它们）

| 名词 | 大白话解释 |
|---|---|
| **BFF**（Backend For Frontend，"为前端服务的后端"） | 浏览器不直接访问 Node，而是访问 Java（8080 端口），Java 帮它去调 Node（3001 端口）。好处：签名、token 全留在服务端，浏览器 Cookie 里只有会话 ID。 |
| **包络**（envelope） | 所有接口返回的统一外壳 `{code, message, data, trace_id}`。`code=0` 才是成功；`data` 才是业务数据。Java 的 `NodeApiClient` 和前端的 `http.ts` 都会自动"剥壳"，你拿到的直接就是 data。 |
| **权限码** | 形如 `system:user:query` 的字符串，代表"对系统-用户模块-有查询权"。登录后 `/api/me` 会把当前账号的所有权限码下发到前端；前端用 `can(code)` 决定菜单/按钮显不显示，Node 用 Casbin 决定接口放不放行。**永远不要写 `role === 'ADMIN'` 判断**。 |
| **幂等键**（Idempotency-Key） | 所有写请求（POST/PUT/PATCH/DELETE）必须带的一个随机字符串头，Node 靠它防止"网络重试导致重复下单"。Java 客户端自动补，你不用管。 |
| **CSRF**（Cross-Site Request Forgery，跨站请求伪造） | 浏览器自动带 Cookie 的特性可能被恶意网站利用。防御办法：Cookie 里放一个 `XSRF-TOKEN`，写请求时前端自动把它放到 `X-XSRF-TOKEN` 头里回传。前端的 `http.ts` 已自动处理。 |

### 0-2 开工第一件事：同步依赖（`npm install`）

> 这一节是真实踩坑后补的。**拉完别人的代码，第一件事永远是 `npm install`**，否则编译必炸。

**为什么会缺包**：`node_modules`（依赖包实际安装目录）从来**不进 git**（被 `.gitignore` 忽略，因为它有几千个文件），但 `package.json`（依赖清单，几行字）**会进 git**。所以组员3 在 S1 里给 `package.json` 加了两行依赖（`kafkajs` 秒杀 MQ 客户端、`pino` 结构化日志库），你 `git pull` 之后代码就比本地的依赖包新——编译时自然找不到。

**你会看到的现象（10 条报错，其实只有 1 个原因）**：

```text
src/lib/logger.ts:2:18  - error TS2307: Cannot find module 'pino' or its corresponding type declarations.
src/mq/kafka.ts:1:53    - error TS2307: Cannot find module 'kafkajs' or its corresponding type declarations.
src/mq/consumer.ts:220:33 - error TS7031: Binding element 'topic' implicitly has an 'any' type.
src/mq/consumer.ts:220:40 - error TS7031: Binding element 'partition' implicitly has an 'any' type.
... （consumer.ts 一共 8 条隐式 any）
```

**怎么读这些报错**：

| 报错码 | 字面意思 | 真实原因 |
|---|---|---|
| `TS2307 Cannot find module 'xxx'` | TypeScript 找不到这个包的**类型声明** | 包没装进 `node_modules` |
| `TS7031 / TS7006 implicitly has an 'any' type` | 参数推断不出类型 | **连锁反应**：`consumer.ts` 里那 8 个回调参数的类型本来由 kafkajs 的类型定义提供；kafkajs 不在，它们就退化成 any |

**因此结论是：代码一行都不用改。** 判断标准很简单——只要那一串 `implicitly has an 'any'` **全部集中在同一个文件**，且这个文件 import 的包同时报了 `TS2307`，就是依赖缺失，不要逐条去补类型（补了也白补，装完包就自动消失）。

**处理（在 `backend` 目录下跑）**：

```bash
cd E:\colledge\three\软件工程\spro\spro\backend
npm install
```

- **在哪跑**：终端提示符必须是 `.../spro/spro/backend`。跑在项目根目录会装到根 `package.json` 上，白跑一场。
- **期望输出**：末尾出现 `added xx packages`（或 `up to date`）；出现 `npm error` 字样才算失败。
- **验证**：重跑 `npm run build`。**成功时 tsc 一行都不输出**——这是正常现象，不代表没执行。

**下次自己 30 秒定位的口诀**（在**项目根目录** `spro\spro` 下跑这两条，命令里带 `backend/` 前缀；两步对照：清单里有没有 / 本地装没装）：

```bash
# ① 依赖清单里声明了吗？（有 = 组员加过，代码没问题）
grep -n "pino\|kafkajs" backend/package.json
# ② 本地 node_modules 里装了吗？（空 = 需要 npm install）
```

>
> ```bash
> netstat -ano | grep ":6379" | grep LISTENING
> ```
>
> - **有输出** → Redis 已经在跑，**直接跳到 0-4 启动三个服务**，本节剩下的全部跳过。
> - **没输出** → 才需要往下看；只想快速跑通就走下面的「方式 B」（不起 Redis，不影响 S3 验收）。

**顺序**：先确认这三个东西的状态，再去启动服务。下面的命令都在**窗口 4（临时窗口）**敲，任意目录都行——`netstat` 查的是整台电脑的网络，跟当前目录无关。

#### ① 一条命令看全部端口

```bash
netstat -ano | grep -E ":3306|:6379|:3001|:8080|:5174" | grep LISTENING
```

命令拆解：

- `netstat -ano`：列出所有网络连接（`-n` 用数字显示端口，`-o` 多显示一列占用它的进程 PID）
- `grep -E "…"`：只保留包含这些端口号的行
- `grep LISTENING`：只保留"正在监听"的行（已建立连接、TIME_WAIT 的都不要）

**最重要的读法：没有输出 = 那个端口没有服务在监听。** grep 找不到东西时什么都不打印，这不是命令坏了。

| 你看到 | 说明 | 要做什么 |
|---|---|---|
| `TCP 0.0.0.0:3306 0.0.0.0:0 LISTENING 7032` | MySQL 在跑 | 不用管 |
| `TCP …:6379 … LISTENING 12345` | Redis 在跑 | 不用管 |
| **完全没有 3306 的行** | **MySQL 没跑** | 必须处理，见 ② |
| **完全没有 6379 的行** | **Redis 没跑** | 可跳过，见 ③ |
| 完全没有 3001 / 8080 / 5174 | 三个服务还没启动 | 正常，0-4 会起 |

（`[::]:3001` 这种写法是 IPv6 的同一端口，和 `0.0.0.0:3001` 等价。）

#### ② MySQL 没跑：怎么启动

先查服务状态（窗口 4，任意目录）：


期望看到 `Status` 列是 `Running`。如果是 `Stopped`，用**管理员身份**的终端启动（开始菜单搜 Git Bash / PowerShell → 右键"以管理员身份运行"）：

```bash

```

服务名不一定是 `MySQL80`，以上面 `Get-Service` 打印的 `Name` 为准。不想用命令行：`Win + R` → 输入 `services.msc` → 找到名字含 MySQL 的服务 → 右键"启动"。

#### ③ Redis 没跑：三种选择

**第一步永远是先确认它在不在**（别凭印象）：

```bash
netstat -ano | grep ":6379" | grep LISTENING
```

- **有输出** → 在跑，跳过这节。
- **没输出** → 从下面三选一。

**方式 A：用 Docker 起（推荐，本机已装 Docker Desktop）**

1. 开始菜单搜 `Docker Desktop` 打开，等右下角鲸鱼图标停止转圈（首次启动可能要 1~2 分钟）。
2. 验证 Docker 引擎真的起来了：

   ```bash
   docker info --format "{{.ServerVersion}}"
   ```

   - 打印版本号（例如 `29.8.0`）= 引擎就绪。
   - 报 `failed to connect to the docker API … npipe` = 引擎还没起好，继续等，别急着跑第 3 步。
3. 只起 redis 一个容器（在**项目根目录**跑）：

   ```bash
   cd E:\colledge\three\软件工程\spro\spro
   docker compose --env-file backend/.env -f deploy/docker-compose.yml up -d redis
   ```

   - `--env-file backend/.env`：**这一项不能省**，原因见下面的报错说明
   - `-f 文件`：指定编排文件
   - `up -d`：创建并启动，`-d` 表示后台运行（不占窗口）
   - 结尾的 `redis`：**只处理这一个服务**。之所以只点名它，是因为同一份编排里还有 mysql 和 kafka——本机 3306 已被你自己的 MySQL 占着，起容器版 MySQL 会端口冲突。

   **报错 `required variable DB_PASSWORD is missing a value` 是怎么回事**：

   ```
   error while interpolating services.mysql.environment.MYSQL_ROOT_PASSWORD:
     required variable DB_PASSWORD is missing a value:
     Set DB_PASSWORD before starting compose
   ```

   `docker-compose.yml` 第 5 行写的是：

   ```yaml
   MYSQL_ROOT_PASSWORD: ${DB_PASSWORD:?Set DB_PASSWORD before starting compose}
   ```

   读法是「取环境变量 `DB_PASSWORD`；如果没定义，就用 `?` 后面那句话当错误信息直接报错退出」。

   关键点：**Compose 是"先把整份文件解析完，再挑服务启动"**，所以要启动的服务虽然是 `redis`，但 `mysql` 里那个 `${DB_PASSWORD:?...}` 在解析阶段就必须能取到值，否则整个命令直接失败。这跟"我又不起 MySQL"没有关系——它压根没走到挑服务那一步。

   而 `DB_PASSWORD` 只写在 `backend/.env` 里。Compose 默认只读**当前工作目录**（`spro/spro/`）下的 `.env`，那里没有这个文件，所以取不到。

   三种解法，任选：

   | 写法 | 说明 |
   |---|---|
   | `--env-file backend/.env`（推荐） | 明确告诉 Compose 去 `backend/.env` 里找变量，不改任何文件 |
   | `set -a && . ./backend/.env && set +a` 后再跑原命令 | 把变量导进当前窗口。**每开一个新窗口都要重跑**，容易忘 |
   | `docker run -d --name redis -p 127.0.0.1:6379:6379 redis:7.4-alpine` | 完全绕开 Compose，但没有数据卷管理 |

   > 顺带：这条命令会把 `backend/.env` 里的 `JWT_SECRET` 等也一起读进去，但 Compose 只用到自己声明的那个变量，不影响别的。

4. 验证（两条都跑）：

   ```bash
   docker ps --filter name=redis --format "{{.Names}}  {{.Status}}"
   netstat -ano | grep ":6379" | grep LISTENING
   ```

   第一条期望类似 `deploy-redis-1  Up 3 seconds (healthy)`；第二条要有输出。成功启动的输出长这样（容器名前缀是 **`deploy-`** 而不是 `spro-`，因为 Compose 默认拿编排文件**所在目录名**当项目名，`docker-compose.yml` 在 `deploy/` 下）：

   ```text
   [+] Running 2/2
    ✔ Network deploy_default   Created
    ✔ Container deploy-redis-1 Started
   ```

5. 以后想停掉：`docker compose --env-file backend/.env -f deploy/docker-compose.yml stop redis`。

6. **Redis 起来之后**：`backend/.env` 里不用加任何 `REDIS_*` 配置，`backend/src/db/redis.ts` 默认连 `127.0.0.1:6379`，正好对上容器映射。这时起 Node **不要**再带 `REDIS_DISABLED=1`，启动日志里那 3 条 `seckill.warmup.redis_wait_timeout`（约 36 秒）也不会再出现。

**方式 A 卡住了怎么办：双击 Docker 图标「没反应」的排查法**

这不是没启动，而是**引擎启动失败、进程卡在错误态**，所以你点图标只是在给后台发"显示窗口"的信号（日志里那句 `backend already running, signaling show-dashboard` 就是这个意思），窗口自然不弹。

**先看事实**（窗口 4，任意目录）：

```bash
tasklist | grep -i "docker" | head
```

如果能看到 `Docker Desktop.exe` / `com.docker.backend.exe` 若干条 → 进程在跑，问题在引擎。此时去看日志（把 `<你的用户名>` 换成 `win11`）：

```bash
tail -30 "/c/Users/win11/AppData/Local/Docker/log/host/monitor.log"
```

常见错误码与含义（都是真实踩到过的）：

| 日志里的错误码 | 含义 | 对策 |
|---|---|---|
| `Wsl/Service/AttachDisk/MountDisk/HCS/0x800705aa` | 挂着 WSL 的虚拟磁盘时报"系统资源不足" | 残留 VM 锁着 vhdx，`wsl --shutdown` 后重开 |
| `Wsl/Service/CreateInstance/0x80072746` | 创建 WSL 实例时连接被重置 | 同上，通常是上一个 VM 没退干净 |
| **`Wsl/Service/AttachDisk/CreateVm/E_ABORT`**<br>**`Wsl/Service/CreateInstance/CreateVm/E_ABORT`** | **WSL 在"创建虚拟机"这一层就被中止了**（`stdout: 已中止操作`）。注意路径里有 `CreateVm` —— 比上面两个更底层，说明不是 Docker 数据盘的问题，而是**整台机器的 WSL 虚拟机都起不来**，任何 WSL 发行版现在都打不开 | 见下面「E_ABORT 专项」 |
| `无法将磁盘 …docker_data.vhdx 附加到…` | Docker 数据盘挂载失败 | 见下面①~④ |
| `Wsl/Service/CreateInstance/…0x80370102` | 虚拟机平台功能没开 | 控制面板 → 启用或关闭 Windows 功能 → 勾"虚拟机平台"+"适用于 Linux 的 Windows 子系统" → 重启 |

#### E_ABORT 专项：Docker 弹「There was a problem with WSL」对话框

对话框长这样（错误框里那串 `c:\windows\system32\wsl.exe -d docker-desktop …` 就是它内部执行的命令）：

```
There was a problem with WSL
An error occurred while running a WSL command.
...
错误代码: Wsl/Service/CreateInstance/CreateVm/E_ABORT
```

**为什么会 E_ABORT**：WSL 创建虚拟机时需要独占 Hyper-V 的虚拟化资源。如果上一次的 WSL 虚拟机没退干净、或者快速启动把 Hyper-V 状态存成了脏的，新的创建请求就会被"中止操作"打回去。日志里 E_ABORT 往往连续出现十几次——那是 Docker 在反复重试，每次都被打断。

> **别用进程数判断"开了几个实例"**：Docker Desktop 是 Electron 应用，**一个实例本身就有 8~12 个 `Docker Desktop.exe` 进程**（主进程 + 渲染 + GPU + 工具进程）。所以 `tasklist` 里看到十几个同名进程是正常的，不代表你开了十几个实例——实测这台机器单实例就有 12 个。
>
> 判断"是不是有真正的残留"只看一件事：**启动前 `tasklist | grep -i docker` 是不是空的**。不空就说明上次没退干净。

**① 一次性杀掉所有 Docker 进程**（窗口 4，比逐条 taskkill 可靠）：

```bash
taskkill //F //IM "Docker Desktop.exe"
taskkill //F //IM "com.docker.backend.exe"
taskkill //F //IM "com.docker.build.exe"
```

三条都跑完，再 `tasklist | grep -i docker` 确认**一条都不剩**（空输出才算干净）。这一步不能省：只要还有一个后台进程活着，它就会继续锁着 WSL 的虚拟机。

**② 关掉 WSL 并确认状态**（窗口 4）：

```bash
wsl --shutdown
```

然后**换到 PowerShell 窗口**验证（Git Bash 显示 UTF-16 会乱码）：

```powershell
wsl -l -v
```

看到 `docker-desktop  Stopped  2` 就是正常。**如果这条命令本身就报错、或者卡住十几秒才返回**，说明 WSL 服务坏了 → 走 ②.5。

**②.5 重启 WSL 服务**（需要管理员）：

右键开始菜单 → 「终端(管理员)」/「Windows PowerShell(管理员)」→ 粘贴：

```powershell
net stop LxssManager
net start LxssManager
```

期望：先 `LxssManager 服务已成功停止`，再 `LxssManager 服务已成功启动`。如果提示"服务名无效"或"拒绝访问"，说明你不是管理员窗口，重开一个。

**③ 重新启动 Docker Desktop**，只开一个窗口。等 2~3 分钟（第一次重建 WSL 发行版会慢），看托盘鲸鱼图标是否变成"Engine running"。

验证（窗口 4）：

```bash
docker info --format "{{.ServerVersion}}"
```

期望打印一个版本号（本机实测 `29.8.0`，你的可能不同）。**这是唯一可信的成功标志** —— 主界面打开不算，主界面在引擎没起来时也能打开。

**④ 还报 E_ABORT：重启电脑**。这条不是敷衍：Windows 的**快速启动**（Fast Startup）会让"关机再开"保留 Hyper-V 的脏状态，只有点开始菜单 → **重启**（不是关机）才真正清掉。很多人卡在这里两小时，重启一次就好了。

**⑤ 重启后还不行，才动这两个开关**：

1. 控制面板 → 程序和功能 → 启用或关闭 Windows 功能 → 把「**虚拟机平台**」和「**适用于 Linux 的 Windows 子系统**」两个勾**取消** → 重启 → 再重新勾上 → 再重启。（重建 WSL 的底层组件）
2. 升级 WSL：`wsl --update`（在 PowerShell 里跑）

**⑥ 最后：Docker 层面重置**。Settings → Troubleshooting → `Reset to factory defaults`。

> **这一步做完，错误码通常会变**：E_ABORT 消失，变成 `vpnkit-bridge handshake failed`（对话框标题是 An unexpected error occurred）。**这也是进展**，说明 WSL 虚拟机能起了，只是发行版还残缺——直接看下一节，那里有确诊方法和重建方式。

> **判断要不要继续修的时间线**：如果 ①②③ 走完还不行，第 ④ 步重启电脑是性价比最高的一步；重启后仍失败，就别再耗了 —— 你的 S3 任务完全不需要 Redis（见下面方式 B），把 Docker 留到周末有空再弄。

#### 下一阶段错误：`vpnkit-bridge handshake failed`（对话框写 An unexpected error occurred）

错误码会"往前走"，先看清自己卡在哪一步：

```text
Wsl/Service/CreateInstance/CreateVm/E_ABORT       ← WSL 虚拟机起不来
        ↓（按上面 E_ABORT 专项修）
vpnkit-bridge handshake failed: bad magic string  ← 虚拟机能起了，卡在端口转发
        ↓（本节）
engine running，docker info 打印出版本号            ← 成功
```

`vpnkit`（*virtual private network kit*，读 /ˈviːpiːen kɪt/）是 Docker Desktop 的用户态网络栈，负责把容器端口映射到 Windows 本机（`-p 8080:80` 就是它在干活）。它启动时要通过 `%LOCALAPPDATA%\Docker\run\dockerEthernetVfkit` 这个 socket 与后台进程握手，握不上就报这个错。

完整报错长这样（2026-11-26 实测）：

```text
starting engine: resetting socket forwarder: running socket forwarder:
setting up mux: setting up mux options: allocating mux:
vpnkit-bridge handshake failed: unmarshalling handshake: read '<nil>':
not a connection to a multiplexer; received bad magic string '��主机强迫关闭了一个现有的连接。��'
```

逐段读：

- `read '<nil>'` —— 压根没读到对端的数据
- `bad magic string` —— vpnkit 期待读到固定格式的开头（magic string 就是"暗号"），实际读到的是乱码
- `主机强迫关闭了一个现有的连接` —— Windows 的 WSAECONNRESET(10054)，对端把连接掐了
- 合起来：**这条通道的对端根本没活着**，不是数据"脏"了

**根因：WSL 里的 docker-desktop 发行版是残缺的**

**先避开一个弯路**：看到 `run` 目录里 `dockerEthernetVfkit` 是 0 字节、旁边还叠着 `.stale.stale.stale`，很容易判断成"socket 文件坏了，删掉让它重建就行"。

**这个判断是错的。** 实测：全杀进程 + 删 socket + `wsl --shutdown` + 重启电脑，**四样都做完仍然报同一个错**。那些 0 字节文件和 `.stale` 叠代是**结果**，不是原因——删掉之后 Docker 会立刻再生成一批一样的。

真正的证据在 `com.docker.backend.exe.log` 里：

```text
running remote vpnkit bridge: wsl.exe -d docker-desktop -e /usr/bin/vpnkit-bridge ...
[vpnkit-bridge] /run/guest-services/socketforwarder-receive-fds.sock: does not exist yet, waiting for it to be created
→ exit status 1
```

因果链是这样：

1. Docker 在 WSL 里启动 `/usr/bin/vpnkit-bridge`，它要等 `/run/guest-services/socketforwarder-receive-fds.sock` 被创建出来
2. 这个 socket 由发行版的初始化流程 `wsl-bootstrap` 创建
3. 它**迟迟没出现** → `vpnkit-bridge` 等不到就自己 `exit 1` 退了
4. Windows 侧 backend 去连一条已经没人接的通道 → 读到一句错误文本 → `bad magic string`

**为什么 bootstrap 没跑完**：就是前面那几轮 `CreateVm/E_ABORT` 把初始化打断在半路，留下一个半成品发行版。

**一条命令确诊**——量发行版数据盘的大小：

```bash
ls -l "/c/Users/win11/AppData/Local/Docker/wsl/main/ext4.vhdx" | awk '{printf "%s 字节 (%.0f MB)\n", $5, $5/1048576}'
```

| 输出 | 含义 |
|---|---|
| 1 GB 以上 | 发行版是完整的，问题在别处（往下看"其它错误码"） |
| **96 MB 左右** | 空壳：文件系统建好了，初始化没跑完（本机 2026-11-26 实测 96 MB） |

看到 96 MB 就可以确定了：**这类损坏改不动，只能重建。**

**修法：重建 docker-desktop 发行版（二选一）**

**方式 1（推荐，最省事）**：直接点错误对话框上的 **`Reset to factory defaults`**。

它做的事：删除并重建 `docker-desktop` 发行版，清空镜像 / 容器 / 卷。

**代价评估**：本机 Docker 里没有要保留的东西（只用来临时起 redis），代价为零。以后若有重要容器，先 `docker save` 导出再重置。

点完它自动重启引擎，**等 3~5 分钟**（第一次要重新展开 779 MB 的 `docker-desktop.iso`，比平时慢很多），然后验证：

```bash
docker info --format "{{.ServerVersion}}"
```

**方式 2（手动，不点按钮）**：先在对话框点 `Quit` 关掉，再在 Git Bash 里：

```bash
wsl --unregister docker-desktop
```

期望输出 `正在注销。` / `已成功注销`。等于直接删掉那个空壳发行版。然后重新双击 Docker Desktop 一次，它会发现发行版不存在，自动从 `docker-desktop.iso` 重新解压一份完整的。

> 上面两种方式都会让 `run` 目录里那堆 `.stale` 残留一起失效，**不需要单独去删 socket 文件**。

**Reset 后仍然失败：重装 Docker Desktop（装回 C 盘）**

本机 Docker 装在 `E:\MovedFromC\DockerDesktop`，靠 `C:\Users\win11\AppData\Local\Programs\DockerDesktop` 这个**软链接**指过去（`C:\Program Files\Docker` 根本不存在）。软链接 + 跨盘在 Docker 升级/自修复时容易出问题。

重装建议：卸载后**装回 C 盘默认位置**（`C:\Program Files\Docker`），不要再用软链接。代价约 2.5 GB C 盘空间（本机 C 盘剩余 48 GB，够）。

#### 如果日志里是 `0x800705aa` / `0x80072746`（不是 E_ABORT）

那通常是残留 VM 锁着数据盘，**不用做上面那套重建**，只做这三步：

```bash
taskkill //F //IM "Docker Desktop.exe"
taskkill //F //IM "com.docker.backend.exe"
taskkill //F //IM "com.docker.build.exe"
wsl --shutdown
```

然后**只启动一次** Docker Desktop。这一类清一次基本就好。

#### 两个与路径有关的坑

- `wsl --shutdown` 的输出如果是乱码（`㩃啜敳獲…`），是 Git Bash 按 UTF-8 显示 Windows 的 UTF-16 所致，命令其实已生效；想看清就换 **PowerShell** 跑 `wsl -l -v`。
- 这台机器曾经把 Docker 数据盘挪到 `E:\MovedFromC\Docker-data`。跨盘的 vhdx 在部分 WSL 版本下更容易挂载失败。**当前（2026-11-26 实测）Docker 已经在用 C 盘路径** `C:\Users\win11\AppData\Local\Docker\wsl\disk\docker_data.vhdx`，所以这条只是备选：真遇到反复挂载失败，再去「Settings → Resources → Advanced → `Disk image location`」改回 C 盘。

> **修 Docker 的时间线建议**：`Reset to factory defaults` 点一下就不用管了（3~5 分钟自己好）。如果连 Reset 都失败、要走重装，那就别在今晚折腾——**本项目只有秒杀/限流用到 Redis**，平台方 9 页和日志三页完全不碰它，直接看下面的方式 B。


**方式 B：不起 Redis，直接继续（本次体检完全够用）**

`backend/src/db/redis.ts` 的设计原则第一条就是"连不上不能拖垮服务"：缓存、令牌桶、库存预扣这些函数在 Redis 不可用时直接返回 `null`，业务自动改成查 MySQL。启动 Node 后看到下面这类日志属于**预期**，不是错误：

```text
{"level":"warn","event":"redis.unavailable",...}
{"level":"info","event":"seckill.warmup.redis_wait_timeout","attempt":1}
```

想明确告诉程序"我不要 Redis，别重试了"，启动时临时加一个环境变量：

```bash
REDIS_DISABLED=1 node dist/server.js
```

（`变量名=值 命令` 的写法只对这一条命令生效，不改 `.env`，也不影响系统环境。）

**方式 C：装 Windows 原生 Redis**（Memurai，或 tporadowski/redis 的 Windows 版），装完当服务运行。Docker 实在起不来才考虑。

**Redis 缺了会损失什么（对照表，别慌）**：

| 功能 | 有 Redis | 没 Redis |
|---|---|---|
| 权限码缓存 | 改权限后要重启 Node + 重新登录才生效 | 每次查库，改完立即生效（调权限反而更省事） |
| 登录失败锁定 | 连续失败 5 次锁定一段时间 | 不锁（演示不受影响） |
| 秒杀库存预扣 | Redis Lua 原子扣减 | 降级 MySQL，高并发下可能 503 |
| 平台 9 页 / 日志三页 | 正常 | **正常**（你这次体检就靠这个） |

### 0-5 补库：`db:check` 报「[缺] xxx 未执行」时怎么做

**先记住一个坑：`npm run db:check` 只检查 8 个脚本**（`backend/src/db/preflight.ts` 第 30~65 行的清单：01/04/05/06/08/11/12/13），**14_logs.sql、15_seckill_window.sql、07、09、10 都不在检查范围**。所以"db:check 全绿"≠"库齐了"——**日志表恰好就是它不查的那一类**。

**在哪个窗口**：窗口 4（临时窗口）。下面命令用了 `../database/…` 相对路径，所以**必须先 `cd` 到 backend 目录**。

**① 补脚本**：

```bash
cd E:\colledge\three\软件工程\spro\spro\backend
set -a && . ./.env && set +a     # 把 .env 里的 DB_PASSWORD 等变量加载进当前窗口，每开一个新窗口都要重跑
MYSQL_PWD="$DB_PASSWORD" mysql -uroot -h 127.0.0.1 --default-character-set=utf8mb4 < ../database/13_im_agent.sql
MYSQL_PWD="$DB_PASSWORD" mysql -uroot -h 127.0.0.1 --default-character-set=utf8mb4 < ../database/14_logs.sql
MYSQL_PWD="$DB_PASSWORD" mysql -uroot -h 127.0.0.1 --default-character-set=utf8mb4 < ../database/15_seckill_window.sql
```

- **成功时 mysql 一行都不输出**（Unix 传统：没问题就不说话），看到输出基本就是 ERROR。
- `set -a && . ./.env && set +a`：把 `.env` 的内容当作环境变量导入当前 shell（`set -a` = 导入的变量对子进程可见），这样下一行才有 `$DB_PASSWORD` 可用，也避免手打密码留在历史里。
- `--default-character-set=utf8mb4` 不能省：13 里有中文注释和种子数据，省了会报 1366。
- **14 / 15 不是幂等的**（14 有 `ALTER TABLE … ADD COLUMN`，15 有 `ADD INDEX`）。重复执行会报 `ERROR 1060 Duplicate column name 'client_ip'` 或 `ERROR 1061 Duplicate key name`——**那说明已经跑过了，跳过即可，不是坏了**。（13 是幂等的：它先查 information_schema 再 PREPARE 执行，重跑安全。）

**② 自查表是否真的建出来（5 行）**

**先搞清楚 SQL 打在哪**——这是新手最常卡的一步。提示符是 `$` 说明你在 bash 里，bash 只认命令不认 SQL，把 `SELECT …` 粘进去会报 `bash: SELECT: command not found` 和 `syntax error near unexpected token '('`（bash 把括号当语法符号）。两种写法：


### 1.2 代码 A：日志查询接口

```java
/* ==================== 日志审计（S3 · T7） ==================== */

/**
 * 日志三页统一数据源：GET /v1/admin/audit/logs（Node 权限码 system:permission:query）。
 * 参数白名单透传：type（login/operation/system）、level（仅 system）、from/to、page/size。
 */
@GetMapping("/api/platform/logs")
public ApiResult<JsonNode> logs(@RequestParam(defaultValue = "1") int page,
                                @RequestParam(defaultValue = "20") int size,
                                @RequestParam String type,
                                @RequestParam(required = false) String level,
                                @RequestParam(name = "from", required = false) String from,
                                @RequestParam(name = "to", required = false) String to,
                                HttpServletRequest request) {
    Map<String, Object> params = new LinkedHashMap<>();
    params.put("type", type);
    if ("system".equals(type) && level != null && !level.isBlank()) {
        params.put("level", level);
    }
    params.put("from", from);
    params.put("to", to);
    params.put("page", page);
    params.put("size", size);
    return ApiResult.ok(node.get("/v1/admin/audit/logs" + query(params),
            Sessions.requireToken(request)));
}
```

**逐行拆解（为什么这么写）**：

- `@GetMapping("/api/platform/logs")`：浏览器将来请求 `/api/platform/logs?type=login&page=1`，由这个方法接住。一页一请求是 BFF 的核心约定（分工 D1 决策），所以日志三页共用**一个**后端接口，靠 `type` 参数区分——这也是《审计页查询参数.md》冻结契约要求的"同一套组件三种查询"。
- `@RequestParam(defaultValue = "1") int page`：URL 上的 `?page=1` 自动变成 int 变量；不传时给默认值，避免空指针。
- `@RequestParam String type`：**必填**。Node 侧 zod 校验 `type` 必须是 `login|operation|system` 三选一，缺了直接 400，所以这里也不给默认值，让错误尽早暴露。
- `level` 参数：Node 规定 `level` **只对 system 类型有效**，传了别的类型会 400。所以这里加 `if ("system".equals(type) && ...)` 才放进参数表——在 BFF 这一层就挡掉一种必然失败的情况。
- `params.put("from", from)` 即使 from 是 null 也放进去：看类里已有的 `query()` 小工具（第 318 行附近），它遇到 null 或空串会**跳过不拼**，所以 null 是安全的"不传"。
- `node.get("/v1/admin/audit/logs" + query(params), Sessions.requireToken(request))`：
  - `node` 是注入的 `NodeApiClient`，签名、幂等键、剥包络、重试它全包了——**这就是 S2 交接件说的"不要重写签名"**。
  - `Sessions.requireToken(request)` 从 Session 里取出登录时存的 Node access token，传给 Node 做 Bearer 认证。
  - 返回值已被剥壳成 `data` 部分（`{list, total, has_more}`），再用 `ApiResult.ok(...)` 包上 Java 自己的包络还给浏览器。
- **为什么手写六个参数而不透传整个 query**：Node 用 zod 的 `.strict()` 校验——**query 里多任何一个字段都直接 400**。透传整串 query 等于把前端随手带的多余参数（比如时间戳缓存穿透参数）原样送给 Node 挨打。白名单是防御性写法。

### 1.3 代码 B：角色权限接口（3 个方法 + 1 个 record）

```java
}

public ApiResult<JsonNode> updateRolePermissions(@PathVariable String id,
                                                 @RequestBody RolePermissionsBody body,
                                                 HttpServletRequest request) {
    Map<String, Object> payload = new LinkedHashMap<>();

    return ApiResult.ok(node.put("/v1/roles/" + numeric(id) + "/permissions", payload,
```

**逐行拆解**：

- `permissions()`：给角色页的"权限树"提供数据。Node 返回 `{list: 菜单树, buttons: 按钮数组, total}`，`list` 是嵌套树（`MenuNode.children`），`buttons` 是扁平数组（每个按钮带 `parent_id` 指明挂在哪个菜单下）。前端负责把按钮拼回树上。
- `rolePermissions()`：`@PathVariable String id` 取 URL 路径里的 `{id}`。`numeric(id)` 是这个类已有的工具方法，用正则 `^[1-9]\d{0,19}$` 先挡一道非法 id——Node 对 id 也是同样校验，本地先挡错误信息更直观。
- `record RolePermissionsBody(...)`：Java 17 的 record，一行定义"只带数据的类"。
  **踩坑点（已实测）**：本工程全局 Jackson 配的是 `property-naming-strategy: SNAKE_CASE`（`application.yml`），
  所以 record 组件名 `permissionIds` 对应的 JSON 字段是 **`permission_ids`**。
  前端必须发 `{"permission_ids": ["1","2"]}`；发驼峰 `permissionIds` 时 Jackson 匹配不上，record 里该字段为 `null`，
  Java 把它原样转给 Node → Node zod 报 `10001 参数为空、格式错误或超出允许范围`，**页面表现就是"点保存没反应、权限也没变"**。

  | 前端 body | Java→Node 结果 |
  |---|---|
  | `{"permission_ids":["10","13"]}` | `200 / code 0`，回读生效 |
  | `{"permissionIds":["10"]}` | `10001 / 参数为空、格式错误或超出允许范围` |

- `updateRolePermissions()`：`payload.put("permission_ids", ...)` 里的 key 是 Node 契约名，**必须手写 snake_case**——`NodeApiClient` 用的是独立 ObjectMapper（不继承全局 SNAKE_CASE 策略），手工转字段名是这个项目的固定写法，你在上面 `agencyPayload`、`createUser` 里能看到同样的模式。

#### 坑：一选时间范围就报 `10001`（Java 把参数编码了两次）

**症状**：不带日期查询正常；一旦在日志页选了时间范围点「查询」，页面顶部红条报

```

```

返回 `code: 10001`。这个文案是 Node 的 zod 校验统一兜底，**不是说你没填参数**。

**排查顺序（别一上来就怀疑前端）**：

| 步骤 | 怎么测 | 结论 |
|---|---|---|
| 1. 绕过 Java 直连 Node | `curl "http://127.0.0.1:3001/v1/admin/audit/logs?type=system&page=1&size=2&from=2026-11-25T16%3A00%3A00.000Z&to=2026-11-27T00%3A00%3A00.000Z" -H "Authorization: Bearer <token>"` | 返回 `code:0` → **Node 没问题**，问题在 Java |
| 2. 看前端产出的格式 | 浏览器 F12 → Network → 点该请求 → 看 `from` | `2026-11-25T16:00:00.000Z`（`toISOString()` 的产物）→ **格式合法** |
| 3. 那就只剩 Java 的转发层 | 见下面 | 二次编码 |

**根因（已用 Spring 6.1.15 实测确认）**：

1. 前端 `toISOString()` → `2026-11-25T16:00:00.000Z`
2. 前端 `qs()` 用 `URLSearchParams` 编码 → `from=2026-11-25T16%3A00%3A00.000Z`
3. Tomcat 解码 → Java 拿到 `2026-11-25T16:00:00.000Z`
4. `PlatformController.query()` 里 `urlEncode()` **又编一次** → `%3A`
5. `NodeApiClient` 用 `client.method(method).uri(path)` 发送 —— **`RestClient.uri(String)` 默认 `EncodingMode=TEMPLATE_AND_VALUES`，会把 `%3A` 再编成 `%253A`**
6. Node 收到的 `from` 是字面量 `2026-11-25T16%3A00%3A00.000Z`（带 `%3A` 五个字符），zod 的 `datetime()` 自然拒绝 → 10001

实测证据（`DefaultUriBuilderFactory` 的输出）：

```
现状：from=2026-11-25T16%253A00%253A00.000Z     ← 二次编码，坏
修复：from=2026-11-25T16%3A00%3A00.000Z         ← 单次编码，好
```

**为什么只有时间参数暴露**：其他查询参数（`status=PAID`、`type=system`、页码）全是纯字母数字，编码一次和两次结果一样，所以一直没被发现。**这是 S2 留下的接缝 bug，不是你的代码写错。**

**修法：改 `java-web\src\main\java\com\example\adminweb\api\NodeApiClient.java`**

⚠️ 这里踩过一个连环坑，直接照抄下面的**最终版**，别用中间版本：
`UriComponentsBuilder.fromUriString(path).build(true).toUri()` 只是"不编码"，得到的仍是一个**相对 URI**（没有 `http://`），
而 `RestClient.uri(URI)` 这个重载**不会**套用 builder 上的 `baseUrl`，会直接抛
`IllegalArgumentException: URI with undefined scheme` → 接口 500（验证码、登录全挂）。
所以必须自己把 `baseUrl + path` 拼成绝对地址。

import 区加：

```java
import java.net.URI;
```

字段与构造器加 `NodeProperties`（Spring 会自动注入）：

```java
private final String baseUrl;

public NodeApiClient(RestClient nodeRestClient, RequestSigner requestSigner, NodeProperties properties) {
    this.client = nodeRestClient;
    this.signer = requestSigner;
    String configured = properties.baseUrl() == null ? "" : properties.baseUrl();
    this.baseUrl = configured.endsWith("/") ? configured.substring(0, configured.length() - 1) : configured;
}
```

`execute()` 里把这一行：

```java
RestClient.RequestBodySpec spec = client.method(method).uri(path).headers(h -> headers.forEach(h::set));
```

改成：

```java
// 两个要求同时满足，只能用 URI.create 自拼绝对地址：
// 1) uri(String) 会二次编码 %XX（%3A → %253A）；
// 2) uri(相对URI) 不套 baseUrl，抛 URI with undefined scheme。
// URI.create 只解析不编码，正好保留 controller 侧 URLEncoder 编好的 %XX。
URI target = URI.create(baseUrl + path);
RestClient.RequestBodySpec spec = client.method(method).uri(target).headers(h -> headers.forEach(h::set));
```

**为什么不用 `build(true)`**：它的 `true` 是 `encoded=true`，只管"别再编码"，不管"补 scheme"。
两个诉求必须分开满足，所以最终选 `baseUrl + path` 再 `URI.create`。

**改完必须重启 Java**（同本节开头那三步），然后重新登录，再试一次时间范围查询——期望表格只剩范围内的时间行。
**注意按表格上显示的时间去选区间**：时间列已经转成本机时区（UTC+8），如果你挑的区间在表格里压根没有行，返回空是正常的（见 2.5 第 8 条的时区说明）。
**顺手回归验证码**：退出登录 → 登录页应能看到图形验证码（这正是上面那个 500 的现场）。

> 单元测试里已加了回归用例 `相对path能拼上baseUrl且已编码的百分号不被二次编码`（`NodeApiClientTest`），
> 改完跑 `./mvnw -q test -Dskip.frontend=true -Dtest=NodeApiClientTest` 应为 5 个用例全绿。

> **R3 纪律**：`NodeApiClient.java` 是 S2 建的文件、所有接口都过它。这次改动已登记到 `docs/plan/Node问题单.md`（编号 #2），记录「改了什么、为什么、影响面」。你自己动手改的话，也照那个模板补一条。

```tsx
            { title: '时间', dataIndex: 'time', width: 180, render: renderTime },
            {
              title: '级别', dataIndex: 'level', width: 90,
              // level 是 pino 的数字级别，必须先映射成名字再上色，否则 LEVEL_COLORS 永远命中 default
              render: (v: unknown) => {
                const name = levelName(v)
                return <Tag color={LEVEL_COLORS[name] ?? 'default'}>{name.toUpperCase()}</Tag>
              },
            },
            // 内容字段：本项目 logger 用的是 `event`（如 auth.login），标准 pino 才会用 `msg`。
            // 两个都取，先 msg 后 event，兼容两种写法。
            {
              title: '内容', dataIndex: 'event', ellipsis: true,
              render: (_: unknown, row: LogRow) => <Tooltip title={s(row.msg ?? row.event)}>{s(row.msg ?? row.event)}</Tooltip>,
            },
            { title: 'trace_id', dataIndex: 'trace_id', width: 120, ellipsis: true, render: s },
          ]

  return (
    <Card
      title={TITLE}
      extra={
        <Space wrap>
          <DatePicker.RangePicker
            showTime // 日志精确到毫秒，不开 showTime 只能选到"天"，过滤没意义
            format="YYYY-MM-DD HH:mm" // 显示到分钟就够，秒全打出来输入框会挤成两行
            value={range}
            onChange={(values) => setRange(values && values[0] && values[1] ? [values[0], values[1]] : null)}
          />
          <Select
            allowClear
            placeholder="级别"
            style={{ width: 110 }}
            disabled={type !== 'system'} // Node 契约：level 仅 system 有效
            value={level}
            onChange={(v) => setLevel(v)}
            options={['trace', 'debug', 'info', 'warn', 'error', 'fatal'].map((v) => ({ value: v, label: v.toUpperCase() }))}
          />
          <Button type="primary" onClick={applyFilters}>查询</Button>
          <Button icon={<ReloadOutlined />} onClick={() => void load()} loading={loading} />
        </Space>
      }
    >
      {error && <Alert type="error" showIcon message={error} style={{ marginBottom: 12 }} />}
      <div style={{ marginBottom: 10, color: '#8c8c8c', fontSize: 12 }}>
        表格内时间为本机时区（{tzLabel}）；筛选取的也是本地时间，查询时会自动换算成 UTC 去库里比对。
      </div>
      <Table<LogRow>
        rowKey={type === 'system' ? (_, index) => `sys-${index}` : 'id'}
        loading={loading}
        dataSource={rows}
        pagination={{
          current: page, pageSize: size, total,
          showSizeChanger: true,
          showTotal: (value) => `共 ${value} 条`,
          onChange: (nextPage, nextSize) => { setPage(nextPage); setSize(nextSize) },
        }}
        columns={columns}
      />
    </Card>
  )
}
```

**关键设计逐条拆解**：

- **为什么三页共用一个组件**：分工 S3 第 3 项原话"同一套组件三种查询"。分页、时间范围、刷新逻辑完全一样，只有列定义不同——抽成一个 `LogPage`，三页各写 3 行薄壳（见 2.3），以后改分页逻辑只改一处。这就是"能自证的审计证据"的工程化做法。
- **`applied*` 与 `range/level` 分离**：antd 的 RangePicker 每点一次日期面板都触发 `onChange`。如果筛选直接进了 `load` 的依赖数组，选个日期会连发好几个请求。**"选择态"和"生效态"分离**是筛选类页面的标准手法。
- **`setPage(1)` 在 applyFilters 里**：假设你停在第 5 页，然后筛选"只看 error"，结果只剩 3 条——不回第 1 页就会请求一个空页。
- **`toISOString()`**：dayjs 的这个方法输出 UTC 时间并以 `Z` 结尾，恰好满足 Node zod 的 `datetime({offset:true})` 校验（`Z` 和 `+08:00` 都合法）。注意**必须带时区**，裸的 `2026-11-26T08:00:00` 会被 Node 直接 400。它同时完成了**本地 → UTC 的换算**：你选 00:00（本地），发出去是前一天 `16:00:00.000Z`，Node 直接拿这个字符串跟库里的 UTC 墙钟比大小，口径一致。
- **时间列必须 `renderTime`，不能 `render: s`**：这是最容易误判成"筛选坏了"的坑。数据库 `sys_operation_log.created_at` 存的是 **UTC 墙钟**（`backend/src/db/connection.ts` 里 `timezone:'Z'`，写入读出一律按 UTC），API 原样吐 `2026-11-27T02:08:45.747Z`。如果你直接把字符串打到表格上，看到"02:08"就会以为那是本地凌晨 2 点，然后去筛 00:00–06:00，结果 0 条——其实那条日志的本地时间是 **10:08**。`fmtTime` 用 `dayjs(ISO).format()` 转成本机时区，显示与筛选口径才对齐。实测对照（同一批数据）：

  | 表格显示 | 你筛的区间 | 结果 | 判定 |
  |---|---|---|---|
  | `02:08`（UTC 原样，**旧版**） | 本地 00:00–06:00 | 0 条 | 看着像 bug，其实是显示骗了你 |
  | `10:08`（本地，**新版**） | 本地 00:00–06:00 | 0 条 | 正确：这条日志确实不在凌晨 |
  | `10:08`（本地，**新版**） | 本地 08:00–12:00 | 14 条 | 正确 |
- **`rowKey`**：antd 表格要求每行有唯一 key。login/operation 行有数据库 `id`；pino 系统日志行没有 id，用行号兜底（`sys-${index}`）。
- **`s()` 兜底**：MySQL 的 DATETIME(3) 经 JSON 序列化、`COUNT` 走字符串……字段类型不完全可控，`String()` 统一转换 + 空值显示 `—`，是这些页面里防"白屏/undefined"最便宜的手段。
- **脱敏约定**：`login_name`、`masked_phone` 这类字段是 Node 写库前就脱敏好的（中间四位打码），前端**只负责展示、绝不尝试还原**——这是 T7 的红线："抓一条日志行，肉眼看不到完整手机号"。

```tsx

/** /v1/permissions 的按钮节点（types.ts 里已声明 PermissionButton，这里直接 import 也行） */
import type { PermissionsPayload } from '../../lib/types'

/** 把 Node 的"菜单树 + 扁平按钮"拼成 antd Tree 要的 DataNode 结构：
 *  按钮按 parent_id 挂回所属菜单节点下面。没有父级的按钮丢弃（本项目没有这种数据，防御一下）。 */
function buildTree(menus: MenuNode[], buttons: PermissionsPayload['buttons']): DataNode[] {
  const byParent = new Map<string, PermissionsPayload['buttons']>()
  for (const b of buttons) {
    if (!b.parent_id) continue
    const bucket = byParent.get(b.parent_id) ?? []
    bucket.push(b)
    byParent.set(b.parent_id, bucket)
  }
  // 递归转换；label 带上 code 方便对权限码（演示时老师看得懂）
  function convert(node: MenuNode): DataNode {
    const childMenus = (node.children ?? []).map(convert)
    const childButtons = (byParent.get(node.permission_id) ?? []).map((b) => ({
      key: b.permission_id,
      title: `${b.name}（${b.code}）`,
    }))
    const children = [...childMenus, ...childButtons]
    return {
      key: node.permission_id,
      title: `${node.name}（${node.code}）`,
      children: children.length > 0 ? children : undefined,
    }
  }
  return menus.map(convert)
}

/** 收集树里所有 key（用来判断"角色已授权 id 里哪些真实存在于当前权限树"） */
function collectKeys(nodes: DataNode[], into: Set<string>): void {
  for (const n of nodes) {
    into.add(String(n.key))
    if (n.children) collectKeys(n.children, into)
  }
}

/** 只收集叶子 key：Tree 勾选态用叶子渲染最稳（父节点勾选态由 antd 自动推导），
 *  保存时 Node 会自动补齐祖先菜单，所以只回传叶子不会丢权限。 */
function leafKeys(nodes: DataNode[], into: Set<string>): void {
  for (const n of nodes) {
    if (n.children && n.children.length > 0) leafKeys(n.children, into)
    else into.add(String(n.key))
  }
}

      setError(e instanceof ApiError ? e.message : String(e))
      setDrawerRole(null)
    } finally {
      setLoadingTree(false)
    }

  }
```

**关键设计逐条拆解**：

- **`Promise.all` 并行**：权限树和已授权 id 是两个独立接口，串行发要等两次网络往返，并行只要一次。
- **为什么勾选态只放叶子**：antd Tree 的勾选有"父子联动"——如果直接把父节点 id 塞进 `checkedKeys` 而它的子节点没全勾，展示会矛盾。只放叶子，父节点勾选态由 antd 根据"子节点是否全勾"自动推导（全勾显示 ✓，部分勾显示半选）。保存时把 `onCheck` 给的完整勾选集合（含自动勾上的父节点）发回去即可；**Node 会再补一遍祖先菜单**，双保险。
- **`message.success(...)` 里的提示语不是废话**：权限改完后 Session 里的 `node.permissions` 还是旧的（S2 交接件写明"改角色后必须重新登录才生效"），这句话在演示时是老师会追问的点，界面提前说了。
- **`onCheck={(keys) => setCheckedKeys(keys as string[])}`**：antd 的 onCheck 返回类型在联动模式下就是 `Key[]`，`as string[]` 是把 antd 的 `Key`（string | number）收窄成 string——我们的 key 全来自 `permission_id`（Node 已转字符串），所以安全。
- **为什么不做"新建角色/删除角色"**：分工 S3 第 1 项的要求是"roles+permissions 页面"完成治理闭环；新建/删除在极限档属于 P2（砍 P2 不砍关键路径）。而且删除有连锁约束（内置角色删不得、有用户的角色删不得），留给有余力时再加，避免演示翻车。

**逐行解释**：

| 行 | 做了什么 | 为什么 |
|---|---|---|
| `import { Button, Result } from 'antd'` | 引入 Ant Design 的 `Result`（整页状态展示组件）和 `Button` | `Result` 自带大图标 + 标题 + 副标题 + 操作区的版式，403/404/500 这类页面用它最省事，也不用自己写 CSS |
| `import { useNavigate } from 'react-router-dom'` | 引入路由跳转钩子 | 按钮要能跳走，不能用 `<a href="/">`——那会整页刷新，登录态（内存里的 Session 靠 cookie，但 SPA 状态会重来）不划算 |
| `export default function ServerErrorPage()` | 默认导出组件 | `App.tsx` 里 `import ServerErrorPage from '...'` 用的就是默认导出。**default 和具名导出搞错是最常见的"组件渲染成 undefined"原因** |
| `const navigate = useNavigate()` | 拿到跳转函数 | 只能在组件内部调用（Hook 规则：不能放在 if/循环里，也不能在组件外调用） |
| `status="500"` | 用 AntD 内置的 500 视觉 | 顺手拿到配套插画和配色，跟 403/404 视觉一致 |
| `title="500"` / `subTitle="…"` | 大字标题 + 说明文案 | 用户看到的是中文解释，不是裸的 HTTP 码 |
| `extra={ <Button …> }` | 操作区 | 给用户一条出路，别让人卡在错误页 |
| `navigate('/')` | 跳根路径 | `App.tsx` 里 `/` 已重定向到 `/agency/dashboard`（`<Route path="/" element={<Navigate to="/agency/dashboard" replace />} />`），所以这里写 `/` 就够了，不用写死工作台路径 |

路由已在第 2.4 步加过（`<Route path="/500" element={<ServerErrorPage />} />`）。浏览器访问 `http://localhost:5174/500` 应直接看到页面。

**为什么补它**：分工 S3 第 5 项要求 `403/404/500` 三件套。403（S2 已建 ForbiddenPage）、404（S2 已建 NotFoundPage）都有，就差 500。文案里提 `trace_id` 是因为日志页能按 trace_id 查上下文——错误页和日志页在这里形成呼应，答辩可以讲。

```markdown
|---|---|---|---|
| GET | `/api/platform/logs` | system:permission:query | 日志三页统一入口；query：type(login/operation/system 必填)、level(仅 system)、from/to(ISO-8601 含时区)、page、size；返回 {list,total,has_more} |
| GET | `/api/platform/permissions` | system:permission:query | 权限树 + 按钮清单（角色页数据源） |
| GET | `/api/platform/roles/{id}/permissions` | system:role:query | 角色已授权 permission_id 列表 |
| PUT | `/api/platform/roles/{id}/permissions` | system:role:update | 全量覆盖授权；body: **{permission_ids:[...]}**（snake_case，发驼峰会被 Java 的 SNAKE_CASE 策略丢掉→10001）；Node 自动补祖先菜单 |
| GET | `/api/platform/overview` 等其余 9 页聚合接口 | 见各页 | 与 PlatformController 一一对应，字段透传 snake_case |

写接口均需 CSRF 头 X-XSRF-TOKEN（前端自动携带）；幂等键与 HMAC 签名由 BFF 服务端补齐，浏览器不接触任何令牌。
```

## 附录 · 常见报错速查

| 症状 | 原因 | 处理 |
|---|---|---|
| `npm run build` 报 `TS2307 Cannot find module 'pino' / 'kafkajs'` | 拉了新代码但没同步依赖（`node_modules` 不进 git，`package.json` 进了） | `cd backend && npm install`，然后重跑 build。详见第 0-2 节 |
| `npm run build` 报一串 `TS7031 / TS7006 implicitly has an 'any' type` | **多是上面那条的连锁反应**：参数类型由缺失包的类型声明提供 | 先修 `TS2307`（装依赖），这串会自动消失；千万别逐条改类型 |
| `db:check` 全 `[OK]` 但日志三页空表 / Node 写日志报错 | 14_logs.sql 不在 db:check 覆盖范围，可能没跑 | 查 `sys_login_log` 是否存在；不存在就补跑 14，见第 0-5 节 |
| 跑 SQL 报 `ERROR 1060 Duplicate column name` / `ERROR 1061 Duplicate key name` | 14 / 15 不是幂等脚本，已经跑过一遍了 | 跳过即可，不是错误 |
| 页面报"权限不足，禁止访问"（403） | 权限码没授权（先查第 0-8 节的 SQL 有没有跑）或账号角色不对 | 查 `sys_role_permission`；改完**重启 Node + 重新登录** |
| 400「参数为空、格式错误或超出允许范围」（code 10001） | Node zod `.strict()` 拦截：query 多传字段 / from 不带时区 / level 用在非 system | 对照《审计页查询参数.md》逐个核对参数 |
| 日志页选了时间段但**一条都查不到**，可表格里明明有行 | 时间列还按 UTC 原样显示（`02:08` 其实是本地 `10:08`），你在按错的时间找 | 已修：时间列转本机时区。**按表格上看到的几点去筛**；先筛本地 08:00–12:00 验证连通，再筛真实区间。见 2.5 第 8 条 |
| 时间列显示 `2026-11-27T02:08:45.747Z`，或日期和时间折成两行 | 时间列还是 `render: s`，把 ISO 字符串原样打上去了 | 换成 2.2 的 `renderTime`（dayjs 转本地时区 + `whiteSpace: nowrap`） |
| 浏览器地址栏访问 `/api/platform/xxx` 返回 `{"code":40400,"message":"接口或资源不存在：api/platform/xxx"}` | **Java 没重新编译/重启**。`40400` 是 `GlobalExceptionHandler.java:30` 的 `NoResourceFoundException`，即 Spring 路由表里没这条，跟参数无关 | 比对源码与 `target/classes` 的时间戳 → 窗口 2 `Ctrl+C` → `./mvnw spring-boot:run -Dskip.frontend=true` → 等 `Started AdminWebApplication` → **重新登录**。见第 1.4 节 |

| 提交写操作报 CSRF 校验失败 | 少了 `X-XSRF-TOKEN` 头 | 别手写 fetch，一律用 `lib/http.ts` 的 `api.post/put` |
| Vite 终端满屏红色 TS 报错 | 类型名抄错 / 忘了 import | 看第一条报错（后面的多是连锁），对照本教程代码 |

| `taskkill` 报 `Invalid argument/option` 或找不到 PID | Git Bash 把单斜杠 `/PID` 当成路径转换了 | 用 `//PID` `//F`（双斜杠），或改用 PowerShell 的 `Stop-Process -Id xxx -Force` |
