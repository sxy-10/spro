## 1. 为什么这个项目可以串行

并行分工的问题是"人和人互相等接口"；串行的代价是**日历工期 ≈ 总人日**。你们选串行，是因为下面三条收益在这个项目里特别值：

1. **零文件冲突**：同一时刻只有一个人在写代码，不需要定"谁先合、谁 rebase"。
2. **每个阶段都有可运行出口**：阶段未过出口判据不进下一阶段，问题不会滚到答辩前。
3. **责任唯一**：某个功能坏了，看阶段归属就知道找谁，不存在"这是前端还是后端的问题"。

代价必须说清：总工作量约 **37 人日**，串行下来就是 **37 个工作日**。所以第 7 节给了三档工期，你按剩余周数选一档，**选完再开工**。

## 8. 你的验收（S7）

验收不用看代码，按这张表逐条当场演示，全部通过才算交付。

| # | 判据 | 怎么验（当场做） |
|---|---|---|
| 1 | 单 jar 可交付 | 清空 `static/` → `./mvnw package` → `java -jar` → `:8080` 直出登录页 |
| 2 | 浏览器无令牌 | F12：Cookie 只有 `JSESSIONID` 与 `XSRF-TOKEN`；请求头无 `Authorization`/`X-Signature` |
| 3 | CSRF 生效 | 带 Cookie 但删掉 `X-XSRF-TOKEN` 发写请求 → 403 |
| 4 | 权限可区分 | 三种角色登录后菜单不同；社管手改 URL 进 `/platform/roles` → 403 |
| 5 | 秒杀语义未变 | `POST /v1/seckill/:routeId` 与 `GET /v1/seckill/result/:reqId` 行为与改造前一致 |
| 6 | Kafka 语义正确 | 关消费者 → lag 上涨；开消费者 → 补单；同一 `reqId` 重投不重复 |
| 7 | 定时器是框架不是循环 | 日志有任务名/耗时/结果；人为让一个任务抛异常，其他三个照常 |
| 8 | 内部接口不可达 | 用公网地址访问 `/internal/timers/expire-orders` → 404 |
| 9 | 日志三类齐全 | 一次登录 + 一次点赞 + 一次改权限 → 三页各有记录且已脱敏 |
| 10 | 推荐链路通 | 造 200 条行为 → Redis 有画像 → 端上"为你推荐"与行为相关 |
| 11 | 大屏真在动 | 停掉预聚合任务 → 数字停更；恢复 → 继续更新 |
| 12 | 文档一致 | 随机抽 3 个接口，`API_V1.md` 与实际返回逐字段对得上 |

**建议验收顺序（20 分钟）**：① 启单 jar → 登录看 Cookie（2、1）；② 权限切换（4）；③ 大屏停更（11）；④ 秒杀压测与 lag（5、6）；⑤ 日志三页（9）；⑥ 停 Kafka 看 503（隐性加分）；⑦ 内部接口 404（8）；⑧ 推荐（10）；⑨ 文档抽查（12）。
