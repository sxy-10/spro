# IM 群聊扩散选型（写扩散 / 读扩散 / 混合）

> 第 3 棒（组员3）交付物 · 2026-11-20
> 一句话结论：**本项目选读扩散**（`im_message` 单份存储 + 参与者游标 `last_read_seq`），写扩散作为演进方向保留。

---

## 一、要解决的问题

一条群消息发出后，群里 N 个人都要能收到。怎么"投递"和"存储"，业界有两条经典路线：

- **写扩散**（fan-out on write，/fæn aʊt/，扇出写在扩散时）：消息只存一份不行，要给每个成员各写一份"收件箱"，读的时候只读自己的收件箱。
- **读扩散**（fan-out on read，扇出在读取时）：消息在会话里**只存一份**，谁要看就按会话 + 游标去拉。

---

## 二、三种方案对比

| 维度 | 写扩散（一人一份收件箱） | 读扩散（会话内单份存储） | 混合（微信/钉钉实际做法） |
|---|---|---|---|
| 写入次数（群 N 人） | 1 → **N 份** | **1 份** | 单聊写扩散，大群读扩散 |
| 读取成本 | 低（读自己收件箱，天然有序） | 中（按会话 + seq 范围拉） | 按会话规模分流 |
| 写放大 | 群越大越炸（500 人群 = 500 倍写） | 无 | 折中 |
| 成员变动 | 新成员要回填历史，退群要清理 | 无需处理，天然对齐 | — |
| 已读/未读 | 收件箱天然支持 | 需要额外游标（`last_read_seq`） | 游标 |
| 典型适用 | 小群、通知类、读多写少 | 大群、消息量大、写多 | 单聊/小群 + 超大群 |

**为什么写扩散在超大群会崩**：1000 人群发一条消息写 1000 行，发 10 万条消息就是 1 亿行；且成员入群/退群/漫游历史都要额外维护，一致性极难保证。

## 三、本项目的选择与理由

### 3.1 现状：本质是读扩散

| 环节 | 实现 | 位置 |
|---|---|---|
| 存储 | 会话内**单份**存消息，`UNIQUE(conversation_id, seq)` 保证会话内 seq 连续 | `im_message`（`database/11_im.sql`） |
| 发号 | 行锁 `SELECT last_message_seq FOR UPDATE` +1，事务内落库 | `im/messageService.ts` `send()` |
| 在线投递 | `hub.sendToConv()` 按连接表把帧推给在线成员 | `im/hub.ts` |
| 离线补偿 | 全员离线时投 `im:notify`，消费者按参与者 `INCR im:offline:{uid}` | `mq/producer.ts` / `mq/imNotifyConsumer.ts` |
| 增量对账 | 客户端带 `lastSeq` 发 `sync` 帧，服务端重放 `seq > lastSeq` 的消息 | `im/wsServer.ts` `case 'sync'` |
| 已读 | 每人一行游标 `im_participant.last_read_seq`，`GREATEST` 只进不退 | `im_participant` |

消息**只有一份**，N 个成员靠"在线直接推 + 离线计数 + 重连按游标拉"各自对齐，这正是读扩散。

### 3.2 为什么课堂项目选读扩散

1. **写放大为 0**：一条群消息只写 1 行，seq 由会话行锁统一分配，天然全局有序，不需要给 N 个人分别发号。
2. **一致性简单**：单一数据源，不会出现"张三的收件箱有这条、李四的没有"的漂移；删消息/撤回也只改一处。
3. **已读需求已被游标满足**：本项目的"已读/未读"用 `last_read_seq` 对比 `last_message_seq` 就够了，不需要每人一份收件箱。
4. **成员变动零成本**：新入群直接按会话 seq 拉历史，退群删一行 `im_participant`，不需要回填/清理历史消息。
5. **规模匹配**：课程演示是单机 + 单库 + 几百连接，读扩散的"读时多一次范围查询"完全不构成压力，而写扩散的复杂度（N 倍写、成员回填、漫游）在演示里是纯负担。

### 3.3 什么时候该换成写扩散

出现下面任一信号时，才值得引入写扩散（或混合）：

- 单群成员上万，且消息写入 QPS 高到按会话拉取成为读瓶颈；
- 需要**个性化收件箱**（不同成员看到的列表不同：免打扰、置顶、多端差异化同步）；
- 需要"消息只投给部分成员"（如 @提醒单独收件箱）。

演进路径（不动现有表结构，渐进式）：

1. 新增 `im_inbox(user_id, conversation_id, seq, read_flag)`，主键 `(user_id, conversation_id, seq)`；
2. `send()` 落 `im_message` 后异步（走 `im:notify` 同款 Stream）按参与者批量写 inbox；
3. 读路径切换：先读 inbox，miss 再回落到 `im_message`（双读兜底）；
4. 稳定后下线回落逻辑，`last_read_seq` 退化为 inbox 的聚合视图。

---

## 四、答辩一句话

> 我们消息只存一份，用会话内的 seq + 每个人的已读游标实现投递与已读，本质是读扩散；写扩散的代价是 N 倍写和成员变动回填，课堂规模下没有收益，所以留作演进方向——单聊走写扩散、大群走读扩散的混合模式就是微信的做法，我们给出了切换路径。
