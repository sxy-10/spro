## 第 1 步 · 给 `listSince` 补上 `seq` 列

**做什么**：`backend/src/im/messageService.ts` 第 8~17 行的 `listSince`，SELECT 里没有 `m.seq`。但 sync 帧要按 seq 重放消息，没有 seq 就没法对账。

**怎么做**：把 SELECT 改成（新增 `m.seq,` 一行）：

```ts
    `SELECT CAST(m.id AS CHAR) AS message_id,
            CAST(m.conversation_id AS CHAR) AS conversation_id,
            CAST(m.sender_id AS CHAR) AS sender_id,
            m.seq,
            m.client_msg_id, m.content_type, m.content, m.status, m.created_at
       FROM im_message m
       JOIN im_participant p ON p.conversation_id=m.conversation_id
      WHERE m.conversation_id=? AND p.user_id=? AND m.id>?
      ORDER BY m.id ASC LIMIT 200`,
```

**为什么只加一列**：这个函数是组员2写的，REST 的 `GET /im/messages` 也在用它。加一列不影响老调用（多返回一个字段而已），最小改动原则——不动别人的排序、条件、LIMIT。

> ⚠️ **2026-11-20 更新：此步已由 AI 直接写入仓库并通过冒烟测试**。写的时候踩了 4 个坑，最终代码已修正，注意与初版思路的区别：
> ① `ws.on('message')` 回调是**同步函数**，case 里不能直接 `await`，必须把异步逻辑包进 `void (async () => { ... })(); return;`；
> ② `send()` 收的是 **ServerFrame 对象**，不是 `encodeFrame({...})` 字符串（encodeFrame 是发送前的序列化，广播时传对象）；
> ③ protocol.ts 原本**只有 AckOkFrame 类型没有工厂函数**，已在 protocol.ts 补了 `export function ackOkFrame(clientMsgId, seq)`；
> ④ `messageService.send` 第一参数是 **PoolConnection 不是 Pool**——行锁 `FOR UPDATE` 必须在事务里才有意义，所以 msg 分支要先 `pool.getConnection()` 开事务再调它。

### 2.2 三个分支的完整代码（最终落地版，与仓库一致）

```ts
        case 'msg': {
          // 发号 + 落库 + 广播。messageService.send 内部已做：行锁取 seq、幂等预检
          void (async () => {
            const connIdNum = Number(frame.convId);
            const userIdNum = Number(connection.state.userId);
            const db = await pool.getConnection();   // 行锁必须在事务里，先拿连接开事务
            let sent;
            try {
              await db.beginTransaction();
              sent = await sendMessage(db, connIdNum, userIdNum, frame.clientMsgId, frame.content);
              await db.commit();
            } catch (err) {
              await db.rollback();
              db.release();
              logEvent('im.ws.msg_fail', { convId: connIdNum, err: String(err) });
              send(errorFrame('msg_failed', '消息发送失败，请重试'));
              return;
            }
            db.release();

            // 1) 先给发送者回 ACK（客户端最关心"存上没有，seq 是几"）
            send(ackOkFrame(frame.clientMsgId, sent.seq));

            // 2) 大屏计数（失败不影响主流程）
            void incrBy('im:stat:msg', 1).catch(() => {});

            // 3) 广播给会话内其他人（排除发送者自己）——注意传帧对象，不是 encodeFrame 字符串
            let delivered = 0;
            try {
              delivered = await sendToConv(
                connIdNum,
                {
                  v: PROTOCOL_VERSION,
                  t: 'msg',
                  convId: String(sent.conversation_id),
                  seq: sent.seq,
                  clientMsgId: sent.client_msg_id,
                  senderId: sent.sender_id,
                  type: sent.content_type,
                  content: sent.content,
                  ts: new Date(sent.created_at).getTime()
                },
                { excludeUserId: userIdNum }
              );
            } catch (err) {
              logEvent('im.ws.broadcast_fail', { convId: connIdNum, err: String(err) });
            }

            // 4) 没人在线 → 走 MQ 离线通知（第 3 步实现 publishImNotify）
            if (delivered === 0) {
              void publishImNotify({
                convId: connIdNum,
                seq: sent.seq,
                preview: sent.content.slice(0, 30)
              }).catch((err) => logEvent('im.notify.publish_fail', { err: String(err) }));
            }

            logEvent('im.ws.msg_sent', { convId: connIdNum, seq: sent.seq, delivered });
          })();
          return;
        }

        case 'ack': {
          // 已读回执：推进 last_read_seq。GREATEST 保证"只前进不后退"；两表同事务
          void (async () => {
            const ackSeq = Number(frame.seq);
            const ackConvId = Number(frame.convId);
            const ackUserId = Number(connection.state.userId);
            const db = await pool.getConnection();
            try {
              await db.beginTransaction();
              await db.query(
                `UPDATE im_participant SET last_read_seq=GREATEST(last_read_seq,?)
                 WHERE conversation_id=? AND user_id=?`,
                [ackSeq, ackConvId, ackUserId]
              );
              await db.query(
                `INSERT INTO im_read_cursor (conversation_id, user_id, last_read_seq)
                 VALUES (?,?,?)
                 ON DUPLICATE KEY UPDATE last_read_seq=GREATEST(last_read_seq,VALUES(last_read_seq)), last_read_at=CURRENT_TIMESTAMP(3)`,
                [ackConvId, ackUserId, ackSeq]
              );
              await db.commit();
              logEvent('im.ws.ack', { convId: ackConvId, seq: ackSeq });
            } catch (err) {
              await db.rollback();
              logEvent('im.ws.ack_fail', { err: String(err) });
              send(errorFrame('ack_failed', '已读游标写入失败'));
            } finally {
              db.release();
            }
          })();
          return;
        }

        case 'sync': {
          // 离线同步：把 lastSeq 之后的消息重放给客户端
          void (async () => {
            const lastSeq = Number(frame.lastSeq ?? 0);
            const rows = await listSince(
              Number(frame.convId),
              Number(connection.state.userId),
              0 // listSince 按 id 过滤，这里取全量再按 seq 过滤（量级 <=200 条，够用）
            );
            const replay = rows.filter((r) => Number(r.seq) > lastSeq);
            for (const r of replay) {
              send({                      // 同样传帧对象
                v: PROTOCOL_VERSION,
                t: 'msg',
                convId: String(r.conversation_id),
                seq: Number(r.seq),
                clientMsgId: String(r.client_msg_id),
                senderId: String(r.sender_id),
                type: r.content_type,
                content: r.content,
                ts: new Date(r.created_at as string).getTime()
              });
            }
            logEvent('im.ws.sync_done', { convId: frame.convId, lastSeq, replayed: replay.length });
          })();
          return;
        }
```

**逐块解释"为什么"**：

- **msg 分支为什么只调 `sendMessage`**：发号（行锁 `FOR UPDATE` + `last_message_seq+1`）和幂等（`UNIQUE(sender_id,client_msg_id)` + 预检返回原 seq）组员2已在事务里做完了。你复用它，不重写 = 不引入第二套发号逻辑 = 不会出现重复 seq。
- **先回 ACK 再广播**：发送者最关心"我的消息存上没有"。广播慢一点没关系，ACK 慢了客户端会重发。
- **`delivered === 0` 才发 MQ**：在线的人已经实时收到了，没必要再通知。离线通知的本质是"兜底提醒不在线的人"。
- **ack 用 `GREATEST`**：两个设备交替发 ack（一个读到 seq 5，一个读到 seq 3），如果直接赋值会倒退。`GREATEST(旧值, 新值)` 保证游标只前进——这是老师问的"10 万条批量已读"的核心思路，一条 UPDATE 搞定，不用逐条循环。
- **ack 为什么开事务**：`im_participant` 和 `im_read_cursor` 两张表要一起改，要么都成功要么都不改，避免两表游标不一致。
- **sync 为什么过滤 `seq > lastSeq`**：`listSince` 按 `id>` 过滤（消息 id 全局自增），但客户端存的断点是**会话内 seq**。消息量 ≤200 条，内存过滤最简单且正确；量大才需要 SQL 加 `AND m.seq>?`（文档里写明这个演进方向即可）。

## 第 3 步 · MQ 离线通知（`im:notify` topic）

### 3.1 producer.ts 加发布函数

在 `backend/src/mq/producer.ts` **文件末尾追加**（不动已有的 `publishSeckill`）：

```ts
/* ---------------- IM 离线通知（组员3 · 第 3 棒） ---------------- */

export const IM_STREAM = 'im:notify';

export interface ImNotifyMessage {
  convId: number;
  seq: number;
  preview: string;
}

/** 会话全员离线时投递一条离线通知，消费端按参与者逐个 INCR 离线计数 */
export async function publishImNotify(msg: ImNotifyMessage): Promise<string> {
  const redis = getRedis();
  if (!redis) throw new Error('redis_unavailable');
  const messageId = await redis.xadd(
    redisKey(IM_STREAM),
    'MAXLEN', '~', STREAM_MAXLEN,
    '*',
    'convId', String(msg.convId),
    'seq', String(msg.seq),
    'preview', msg.preview.slice(0, 100)
  );
  if (!messageId) throw new Error('xadd_failed');
  return messageId;
}
```

**为什么照抄 seckill 的模式**：MAXLEN 防止 Stream 无限膨胀（阶段六踩过的坑已经写在文件头注释里）；复用 `getRedis()` 不新开连接；`redisKey()` 保证键有统一前缀。**边界：绝不写 `seckill:stream`，新 topic 只叫 `im:notify`。**

### 3.2 新建消费者 `backend/src/mq/imNotifyConsumer.ts`

参考 `consumer.ts` 的 XREADGROUP 模式新建文件（不是改动它）。

> ⚠️ **2026-11-20 更新：此文件已由 AI 写入仓库**。踩坑记录：`im_device` 表**没有 `online` 字段**（只有 last_seen_at），在线状态实际存在 Redis 的 `im:online:{uid}` hash（presence.ts 维护，TTL 60 秒）——所以离线判定最终用 `EXISTS im:online:{uid}`，不 JOIN im_device。下方代码即为最终落地版。

```ts
/**
 * IM 离线通知消费者（组员3 · 第 3 棒）
 * XREADGROUP 阻塞读 im:notify → 查会话所有参与者 → 在线跳过 / 离线 INCR im:offline:{userId} → XACK
 * 崩溃恢复与 seckill 消费者同理：pending 消息可被重新认领。
 */
import { pool } from '../db/connection.js';
import { getRedis, redisKey } from '../db/redis.js';
import { IM_STREAM } from './producer.js';
import { logEvent } from '../im/protocol.js';

const GROUP_NAME = 'im-notify-group';
const CONSUMER_NAME = `im-notify-${process.pid}`;
const BLOCK_MS = 5000;
const BATCH = 50;

let running = false;

/** 会话所有参与者中，当前不在线（Redis 在线 hash 不存在）的用户 id 列表 */
async function offlineParticipants(convId: number): Promise<number[]> {
  const [rows] = await pool.query<import('mysql2/promise').RowDataPacket[]>(
    `SELECT p.user_id AS userId
       FROM im_participant p
      WHERE p.conversation_id=?`,
    [convId]
  );
  const redis = getRedis();
  if (!redis) return []; // Redis 不可用时安静降级，不堆死信
  const offline: number[] = [];
  for (const r of rows) {
    const uid = String(r.userId);
    const exists = await redis.exists(redisKey(`im:online:${uid}`));
    if (!exists) offline.push(Number(uid));
  }
  return offline;
}

export function startImNotifyConsumer(): () => void {
  const redis = getRedis();
  if (!redis || running) return () => {};
  running = true;
  void (async () => {
    try {
      await redis.xgroup('CREATE', redisKey(IM_STREAM), GROUP_NAME, '0', 'MKSTREAM');
    } catch (err) {
      if (!String(err).includes('BUSYGROUP')) {
        logEvent('im.notify.group_create_fail', { err: String(err) });
      }
    }
    while (running) {
      try {
        const res = await redis.xreadgroup(
          'GROUP', GROUP_NAME, CONSUMER_NAME,
          'COUNT', BATCH, 'BLOCK', BLOCK_MS,
          'STREAMS', redisKey(IM_STREAM), '>'
        );
        if (!res) continue;
        const stream = (res as Array<[string, Array<[string, string[]]>]>)[0][1];
        for (const [messageId, fields] of stream) {
          const map: Record<string, string> = {};
          for (let i = 0; i < fields.length; i += 2) map[fields[i]] = fields[i + 1];
          const convId = Number(map.convId);
          try {
            const users = await offlineParticipants(convId);
            for (const uid of users) {
              await redis.incr(redisKey(`im:offline:${uid}`));
            }
            logEvent('im.notify.consumed', { convId, offline: users.length });
          } catch (err) {
            logEvent('im.notify.consume_fail', { convId, err: String(err) });
          }
          await redis.xack(redisKey(IM_STREAM), GROUP_NAME, messageId);
        }
      } catch {
        await new Promise((r) => setTimeout(r, 1000)); // Redis 抖动时退避 1s 再试
      }
    }
  })();
  return stopImNotifyConsumer;
}

export function stopImNotifyConsumer(): void {
  running = false;
}
```

### 4.1 幂等重发验证 `backend/scripts/test/dupSend.mjs`（新建目录和文件）

> ⚠️ **2026-11-20 晚最终版**（实测两次全 PASS）。初版脚本有两个坑已修：
> ①写接口除 `Idempotency-Key` 外还必须带 **HMAC 签名三件套**（`X-Timestamp`/`X-Nonce`/`X-Signature`），缺了报 `10001`——签名密钥就是 access token，算法见脚本 `signedHeaders()`；
> ②`conversation_id` 必须是**字符串**（项目 ID 统一雪花字符串，传数字报 `10001`）。
> 另外两次发送故意用**不同的 Idempotency-Key**（每次运行随机后缀），才能真正走到"撞 UNIQUE 唯一键"分支，而不是被通用幂等缓存直接回放。

```js
// 验证幂等：同一 client_msg_id 发两次（两个不同的 Idempotency-Key）→ 两次返回同一 seq，库里只有一条
import 'dotenv/config';
import http from 'node:http';
import { createHash, createHmac, randomUUID } from 'node:crypto';

const BASE = process.env.TEST_BASE || 'http://127.0.0.1:3001';
const sha256 = (v) => createHash('sha256').update(v).digest('hex');

const req = (method, path, bodyStr, headers = {}) => new Promise((res, rej) => {
  const r = http.request(BASE + path, {
    method,
    headers: { 'Content-Type': 'application/json',
      ...(bodyStr ? { 'Content-Length': Buffer.byteLength(bodyStr) } : {}), ...headers }
  }, (resp) => { let b = ''; resp.on('data', (c) => (b += c)); resp.on('end', () => { try { res(JSON.parse(b)); } catch { res({ raw: b }); } }); });
  r.on('error', rej);
  if (bodyStr) r.write(bodyStr);
  r.end();
});

// HMAC 签名三件套：X-Timestamp（ISO UTC）+ X-Nonce（16+位随机串）+ X-Signature
// 签名 = HMAC-SHA256(密钥=token, 内容="METHOD\npath\ntimestamp\nnonce\nsha256(body)")，与前端 lib/http.ts 同一套
function signedHeaders(method, path, bodyStr, token, keyLabel) {
  const timestamp = new Date().toISOString();
  const nonce = randomUUID().replace(/-/g, '');
  const signature = createHmac('sha256', token)
    .update(`${method}\n${path}\n${timestamp}\n${nonce}\n${sha256(bodyStr)}`)
    .digest('hex');
  return { 'Idempotency-Key': keyLabel, 'X-Timestamp': timestamp, 'X-Nonce': nonce, 'X-Signature': signature };
}

// ---- 1. 登录 ----
const loginBody = JSON.stringify({ mobile: '13811115678', password: 'Admin@2026' });
const login = await req('POST', '/v1/auth/login', loginBody,
  { 'Idempotency-Key': 'dupsend-login-' + Date.now() });
const token = login.data?.token;
if (!token) { console.error('登录失败:', login); process.exit(1); }

// ---- 2. 同一 client_msg_id 发两次（故意用不同的 Idempotency-Key，
//         才能真正走到 send() 的"撞 UNIQUE(sender_id, client_msg_id) 预检"分支） ----
const CONV_ID = 1; // 已建好的测试会话（tourist01 + tourist02）
const clientMsgId = 'dup-test-' + Math.random().toString(36).slice(2, 10);
const msgBody = JSON.stringify({ conversation_id: String(CONV_ID), client_msg_id: clientMsgId, content: '幂等验证' });

const runSuffix = Date.now().toString(36); // 幂等指纹含 sessionId，固定 key 跨次运行会撞 20015
const r1 = await req('POST', '/v1/im/messages', msgBody,
  { Authorization: `Bearer ${token}`, ...signedHeaders('POST', '/v1/im/messages', msgBody, token, 'dupsend-key-1-' + runSuffix) });
const r2 = await req('POST', '/v1/im/messages', msgBody,
  { Authorization: `Bearer ${token}`, ...signedHeaders('POST', '/v1/im/messages', msgBody, token, 'dupsend-key-2-' + runSuffix) });

console.log('第1次: code =', r1.code, 'seq =', r1.data?.seq, r1.code !== 0 ? JSON.stringify(r1).slice(0, 160) : '');
console.log('第2次: code =', r2.code, 'seq =', r2.data?.seq, r2.code !== 0 ? JSON.stringify(r2).slice(0, 160) : '');

// ---- 3. 查库确认只有一条 ----
let dbCount = '?';
try {
  const mysql = await import('mysql2/promise');
  const conn = await mysql.createConnection({
    host: process.env.DB_HOST || '127.0.0.1', port: process.env.DB_PORT || 3306,
    user: process.env.DB_USER || 'root', password: process.env.DB_PASSWORD,
    database: process.env.DB_NAME || 'travel_agent_db'
  });
  const [rows] = await conn.query('SELECT COUNT(*) c FROM im_message WHERE sender_id=? AND client_msg_id=?',
    [login.data.userId ?? 11, clientMsgId]);
  dbCount = rows[0].c;
  await conn.end();
} catch (e) { console.log('(查库失败，跳过：', e.message, ')'); }

if (r1.data?.seq !== undefined && r1.data.seq === r2.data?.seq && Number(dbCount) === 1) {
  console.log(`✅ 幂等 PASS：两次返回同一 seq = ${r1.data.seq}，库里仅 ${dbCount} 条`);
} else {
  console.log(`❌ FAIL（库里条数 = ${dbCount}）：检查上方响应`);
}
```

**为什么两次返回同一 seq 就算过**（展开版，答辩直接照这段讲）：

想象一个真实场景：你在地铁里发消息，网络抖了一下，APP 没收到服务器的"存好了"回执。APP 的正常做法是**超时后重发同一条消息**（带上同一个 clientMsgId，相当于这条消息的身份证号）。问题是：**服务器到底收没收到第一条？** 如果收到了，重发的那条就绝不能再存一遍，否则聊天记录里出现两条一模一样的"在吗"。

这个项目的防线有两层：

1. **数据库兜底**：`im_message` 表建了唯一索引 `UNIQUE(sender_id, client_msg_id)`——同一个人、同一个身份证号的消息，全表只允许存在一条。第二次 INSERT 会直接被 MySQL 拒绝（报 Duplicate entry）。
2. **代码预检**：`send()` 在插入前先 SELECT 查一次"这组 (sender_id, client_msg_id) 存不存在"，存在就直接把**原消息（含原 seq）返回**，根本不走 INSERT，所以客户端拿到的是 200 成功响应而不是报错——对上层完全透明。

于是验证标准就顺理成章：**发两次同一 clientMsgId → 两次响应里的 seq 相同 + 去库里数只有 1 条**。这三件事同时成立，就证明了"客户端超时重发不会产生重复消息"。答辩时老师问"消息重复怎么防"，答法就是：客户端生成 clientMsgId + 服务端唯一索引兜底 + 预检返回原消息，三个词一句话讲完。

（实测记录：2026-11-20 在 3001 端口连跑两次，均输出 `✅ 幂等 PASS：两次返回同一 seq`，库里仅 1 条。）

### 4.2 批量已读压测 `backend/scripts/bench/batchRead.mjs`

回答老师"10 万人批量已读怎么写"的实证脚本：对比**逐条 UPDATE** vs **一条 GREATEST 批量 UPDATE** 的耗时。

> ⚠️ **2026-11-20 晚最终版**（已由 AI 写入 `scripts/bench/batchRead.mjs` 并实测）。初版有个坑已修：`im_participant.user_id` 有**外键**指向 `sys_user`，直接 `INSERT ... SELECT id BETWEEN 13 AND 5000` 会因为 sys_user 里没这些人而插入 0 行（压测等于没跑）。最终版改为**自建 bench_ 前缀临时用户**，跑完自动清理、可重复运行。

最终版逻辑（文件已在仓库，可直接跑，无需粘贴）：

1. 幂等清理上次残留 → 建 5000 个 `bench_xxxxxx` 临时用户 + 1 个专用压测会话（`conversation_no='BENCHREAD'`，不碰演示会话 convId=1）
2. **A 组**：一个事务里逐条 `UPDATE ... WHERE conversation_id=? AND user_id=?` 循环 5000 次
3. 归零后 **B 组**：一条 `UPDATE im_participant SET last_read_seq=GREATEST(last_read_seq,?) WHERE conversation_id=?`
4. 输出耗时与加速比 → **finally 里自动清理** bench 用户和压测会话

运行：

```bash
cd backend
node scripts/bench/batchRead.mjs          # 默认 5000 人
BENCH_N=200 node scripts/bench/batchRead.mjs   # 想快速验证可先小跑
```

**实测结果（2026-11-20，本机 MySQL）**：

```
压测就绪：会话 4，参与者 5000 人
逐条 5000 人: 867 ms
一条批量 UPDATE: 33 ms
加速比 ≈ 26 倍
```

为什么逐条慢：每条 UPDATE 都要等 MySQL 返回 OK 包（一次网络/进程间往返），5000 条就是 5000 次往返；批量只往返 1 次，剩下的全是数据库内部的行扫描。**答辩话术**："10 万人已读，逐条要 10 万次数据库往返，批量一条 SQL 一次搞定；用 GREATEST 保证游标只前进不后退，乱序到达的已读回执也不会把游标倒退。"
