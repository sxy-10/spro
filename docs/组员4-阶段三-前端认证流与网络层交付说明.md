## 三、分层与请求链路

```text
页面（LoginScreen / ResetPasswordScreen / 组员5 的业务页）
   │  只调语义函数：loginByAccount()、resetPassword()、request()
   ▼
lib/auth.ts        认证语义层：组合接口 + 登录成功后写会话
   │
   ▼
lib/http.ts        Axios 实例
   │  请求拦截：Bearer → Idempotency-Key → X-Timestamp/Nonce/Signature
   │  响应拦截：剥壳 → 401 单飞换票 → 重放 / 清会话
   ▼
lib/session.ts     会话仓库（令牌 + user + permissions），订阅式，UI 自动重渲染
   │
   ▼
useAuth()          React 侧只读视图，组员5 的守卫/按钮权限从这里取数
```

**为什么加 `lib/` 这层而不是继续堆在 `api.ts` 里？**
`api.ts` 现在是「兼容层」，只留老签名转发。真正的新代码按「网络层 / 认证语义 / 状态」三层拆开，任何一层都能单独替换：换 axios、换成 fetch、换成 uni.request（小程序）都只动一层。

## 四、拦截器的四个关键点（答辩重点）

### 1. Bearer 注入：一处写，处处生效

```ts
httpClient.interceptors.request.use(async (config) => {
  const token = getAccessToken();
  if (!internal.skipAuth && token) headers.set('Authorization', `Bearer ${token}`);
  ...
});
```

`skipAuth` 只给登录/注册/换票这三个「还没票」的接口用。业务代码永远不碰 Authorization。

### 2. 写请求的幂等键与防重放签名：**必须保留**

后端 `core.ts` 的 `write()` 强制要求 `Idempotency-Key`；`API_V1.md` 又规定登录后的写请求要带 `X-Timestamp` / `X-Nonce` / `X-Signature`（HMAC-SHA256，密钥 = 当前 token）。改成 axios 时最容易踩的坑是：
axios 默认会自己 `JSON.stringify` 一遍 body，而签名算的是**另一份**字符串 → 后端验签必失败。

所以拦截器里先固定 body 的序列化结果，再对它求摘要，并把同一份字符串交给 axios 发送：

```ts
const rawBody = typeof data === 'string' ? data : JSON.stringify(data ?? {});
config.data = rawBody;                                   // 发出的字节
const digest = await sha256Hex(rawBody);                 // 签名的字节
const message = [method, `/v1${url}`, timestamp, nonce, digest].join('\n');
headers.set('X-Signature', await hmacSha256Hex(token, message));
```

这就是 `api.ts` 里原逻辑的等价迁移，老接口一个都不会坏。

### 3. 剥响应壳：`ApiError` 承载状态码语义

后端响应固定 `{code, message, data, trace_id}`。拦截器不剥壳，每个页面都要写 `res.data.data`，很容易漏。统一在 `request()` 里剥：

```ts
if (body.code !== 0) throw new ApiError(status, body.code, body.message, body.trace_id);
return body.data;
```

`ApiError` 上挂了判断属性，和组员 2 的契约严格对齐：

| 语义 | HTTP | 业务码 | 前端判定 |
| --- | --- | --- | --- |
| 未登录 / 会话失效 | 401 | 20012 | `err.isUnauthorized` |
| 已登录但无权限 | 403 | 20013 | `err.isForbidden` |
| 限流 | 429 | 20014 | `err.isRateLimited` |

**401 和 403 不能混用**：401 才会触发换票，403 换票没有意义（令牌是好的，只是没权限），此时前端应该提示「权限不足」而不是跳登录页。

### 4. 401 单飞换票：并发下只发一次 refresh

真实场景是：页面同时发 5 个请求，令牌刚好过期 → 5 个 401 同时回来。如果每个都去换票，就会打 5 次 `/auth/refresh`，并且可能拿到互相覆盖的令牌。

解决：用一个 Promise 做「单飞」（in-flight 去重），后到的请求等同一个 Promise 的结果：

```ts
let renewing: Promise<boolean> | null = null;
export const renewToken = () => (renewing ??= performRenewal().finally(() => { renewing = null; }));
```

完整闭环：

```text
请求 A、B 同时 401
   ├─ A 进入拦截器 → renewing = performRenewal()  （发 1 次 refresh）
   └─ B 进入拦截器 → 复用同一个 renewing
refresh 成功 → 更新 session 令牌 → A、B 用新令牌重放（各带 retried 标记，最多重放一次）
refresh 失败 → clearSession({expired:true}) → 抛 AuthExpiredError → UI 订阅到 expired → 回登录页
```

三个防死循环的开关：`retried`（每个请求只重放一次）、`skipRefresh`（换票请求自己不再触发换票）、`hasCredential`（匿名 401 不换票）。

## 五、登录 / 找回密码 UI 的设计取舍

- **双 Tab**：`密码登录` / `短信登录`，同一屏内切换，不跳路由（本项目没有 router，用视图状态 `view: login | register | reset`）。
- **图形验证码**：进页面就拉一次；点击图片或「换一张」重拉；**登录失败自动换一张**（一次性验证码不能被重放）。
- **短信 60 秒倒计时**：前端先做「按钮冷却」，同时后端有 `rateLimit('auth:'+ip, 10)` 兜底。倒计时结束才允许重发，切 Tab 不清零（`useCountdown` 在父级持有）。
- **找回密码防枚举**：后端对不存在的手机号也返回成功（`reset-password` 的实现），所以前端文案写成「密码已重置」，不提示「该手机号未注册」。
- **表单校验**：前端校验只为体验（不为安全）。真正的格式校验在后端 `zod`（`mobile` 正则、密码 8–72 位）。前端校验项与后端保持一致，避免「前端放过、后端 400」的割裂。
- **手机号脱敏**：资料接口只返回 `mobile`（`138****0001`），登录页回填时不要拿脱敏值当输入值。
- **关于「PC 端」**：本项目所有页面都装在 `.app-root-wrapper`（固定 390px 手机壳居中）里，这是既有 UI 约定。认证页因此做了三档自适应——窄屏满宽、横屏压缩纵向留白（`max-height:720px`）、宽屏加大留白与点击热区（`min-width:1024px`）。若要做真正的 PC 双栏（左侧品牌图 + 右侧表单），需要同时改 `MobileShell` 的宽度策略，那属于整体 UI 决策，建议和组员 5 一起提。

### 阻塞 3：没有 `/v1/auth/refresh`，401 换票只能降级

1. 接口就绪：`performRenewal()` 打 `/auth/refresh`，返回 `{token, refresh_token}` 即可无缝工作（`access_token` 也兼容）；
2. 优雅降级：该接口 404/405/501 或没有 `refresh_token` 时，自动 `clearSession({expired:true})` 并回登录页，**不会把用户卡在白屏**。

## 十、给组员 5 的接口（你做权限闭环要用）

```tsx
import { useAuth, usePermission } from '../hooks/useAuth';

const { isLoggedIn, user, permissions } = useAuth();   // permissions = { menus, buttons }
const canAddRoute = usePermission('route:line:add');   // 按钮级判定

// 路由守卫：无权限页不许进
if (!isLoggedIn()) return <LoginScreen onLogin={() => {}} />;
if (!canAddRoute) return <p>权限不足，禁止访问</p>;
```

- 登录成功后 `permissions` **已经取好了**（`GET /v1/users/me/permissions`），组员 5 不要再请求一次；
- `permissions.expired === true` 表示「被 401 踢下线」，据此跳登录页并提示；
- 菜单树 `menus` 已由后端排好序、补齐父级，直接递归渲染即可。

## 十一、设计取舍记录（避免后面返工）

| 决策 | 理由 |
| --- | --- |
| 不引入 Redux / Zustand | 状态只有「令牌 + 用户 + 权限」，`useSyncExternalStore` 足够；少一个依赖少一次评审风险 |
| 令牌默认只放内存 | 与 `API_V1.md`「前端只在内存保存令牌，刷新后重新登录」一致；XSS 拿不到持久化令牌。需要「刷新不掉线」时把 `VITE_AUTH_PERSIST=1`，只持久化 `refresh_token` |
| 验证码 id 走请求头 `X-Captcha-Id` | 后端请求体是 `zod.strict()`，多传字段直接 400；走请求头既不改契约也能补丁生效 |
| `api.ts` 保留为兼容层 | 组员 5 与已完成的页面都在 `import { request } from '../api'`，改动面最小 |
| `request<T = any>` | 老代码直接用返回字段；新代码显式标泛型 |
| 刷新失败一律回登录页 | 半登录态比直接登出更难排查 |
