# 组员2 项目讲解（零基础版）

> 面向完全零基础的读者，讲清组员2 在本项目里做了什么、为什么、怎么做。
> 所有术语第一次出现都有大白话解释 + 生活类比。

---

## 一、项目是什么

**项目名**：旅游规划智能体系统（travel-agent）
**目标**：一个旅游平台——B 端（旅行社管理员）在后台管线路、看订单；C 端（游客）用 AI 做行程规划。后端 Node.js + MySQL，前端网页。

**组员2 的位置**：不做业务功能，做**后台权限系统**——"谁能调哪个接口"的判断，以及管理权限本身的 9 个接口。

## 二、为什么要有这套东西（痛点先行）

没有权限系统时，只有组员1 的"登录"——登录完发一个 **JWT**（JSON Web Token，一串加密字符串，相当于**入场手环**，上面写着"我是 3 号用户"）。接口拿到手环只知道**你是谁**，不知道**你能不能干这件事**。

| 场景 | 没有权限系统时 | 后果 |
|---|---|---|
| 游客账号查角色列表 | 直接返回 | 内部数据泄露 |
| 游客账号删角色 | 直接删掉 | 后台瘫痪 |
| 每个接口手写 `if (role === 'ADMIN')` | 9 个接口 9 处判断 | 加第 4 个角色要改 9 个文件，漏一处=越权漏洞 |

**算一笔账**：3 个角色 × 35 条权限 = 105 个格子，其中打了 47 个勾。这 105 个格子全靠数据库 47 行数据表达，**加新角色 = 插几行 SQL，代码 0 行改动**。写成 if 就是几十处硬编码。

> 类比：小区门禁。不是让保安背"张三能进 3 号楼"，而是**给岗位发卡**（保洁卡、业主卡），新人来了发卡就行，门禁认卡不认人。
> 这套思路叫 **RBAC**（Role-Based Access Control，基于角色的访问控制）：**不按人发权限，按岗位发**。

## 三、按动手顺序的六步

### 第 1 步：让"清单"有地方存 —— 建 4 张表

**动作**：写 `database/05_rbac_schema.sql` 并执行。

**命令逐词拆解**：

```bash
mysql -u root -p --default-character-set=utf8mb4 < database/05_rbac_schema.sql
```

| 片段 | 意思 |
|---|---|
| `mysql` | 启动 MySQL 的命令行客户端（能跟数据库"打字聊天"的黑窗口） |
| `-u root` | 用 root 账号登录（最高管理员） |
| `-p` | 回车后输密码（屏幕不显示任何字符是正常的） |
| `--default-character-set=utf8mb4` | 指定文字编码。SQL 文件是 UTF-8，Windows 客户端默认按 GBK 读，读错编码中文变乱码并报 ERROR 1366 |
| `< 文件` | 输入重定向：把整个 SQL 文件"倒进"窗口自动执行 |

**为什么是 4 张表，不是在用户表加一列？**

"加一列" = `sys_user` 表多一竖列写角色。三个真实场景下它坏掉：
1. **一人一岗**：格子装不下两个角色（张三兼任管理员+财务怎么办）；
2. **角色写死**：`role` 列类型是 `ENUM('TOURIST','ADMIN')`——只许填这两个词，加角色要先改表结构再改代码再发版；
3. **有岗无权**：表里写了 ADMIN，但 ADMIN 能干什么？答案在代码里，不在数据里。

4 张表方案：`sys_role`（岗位 3 行）、`sys_permission`（门禁点 35 行）、`sys_user_role`（谁在哪个岗，多对多）、`sys_role_permission`（每个岗能开哪些门，47 行勾）。多对多就像学生选课——必须有一张中间登记表。

**做完应看到**：进入 `mysql>` 交互模式后：

```sql
USE travel_agent_db;
SELECT COUNT(*) FROM sys_permission;      -- 35
SELECT COUNT(*) FROM sys_role;            -- 3
SELECT COUNT(*) FROM sys_role_permission; -- 47
```

`SELECT COUNT(*)` = "数这张表有几行"。数字对上 = 表建好、种子灌好。

**排错**：`ERROR 1366` → 少了 utf8mb4；`Unknown database` → 01 号脚本没跑。

### 第 2 步：给每个"门"起名字 —— 权限码

权限码 = 门牌号，固定三段 `模块:资源:操作`，如 `system:role:add`（能新增角色）、`route:line:query`（能查线路）。

- 不用数字 id 是因为日志里 `required:["system:role:query"]` 一眼看懂，`required:["101"]` 还得翻表；
- **菜单码（两段，如 `system:role`）≠ 按钮码（三段）**。菜单码折算成 `act=view`——"给你看了页面"永远匹配不上"新增/删除"（详见第 2 步末尾的 add/view 澄清）；
- 折算口径集中在 `backend/src/auth/permissionCode.ts` 一个纯函数里。

**动手验证**（可直接照抄）：在 `backend` 目录新建 `check-code.ts`：

```ts
import { toPolicyRequest } from './src/auth/permissionCode.js';
console.log(toPolicyRequest('system:role', 'add'));  // 接口声明「需要新增角色」
console.log(toPolicyRequest('system:role'));          // 用户只有「菜单授权」
```

运行 `npx tsx check-code.ts`，预期输出：

```
{ obj: 'system:role', act: 'add', ... }
{ obj: 'system:role', act: 'view', ... }
```

**add 还是 view 怎么回事？** `toPolicyRequest` 是翻译函数，**喂什么翻什么**：接口声明守卫时喂了动作 `add`，输出就是 add；用户只有菜单授权（没说动作），函数配默认值 `view`。判断"能否新增"时拿 `add` 去比对——用户只有 `view` → `add ≠ view` → 拒绝。没有这个约定，菜单码会变成"该模块所有操作全放行"的万能授权（10 条菜单 = 白送 25 个按钮权限）。
> 类比：电影票。检票口问"有观影票（add）吗？"你掏出的是大堂通行证（view）——能进大楼，进不了影厅。

### 第 3 步：请一个比对引擎 —— Casbin

**Casbin** 是专门做权限比对的第三方库（**库** = 别人写好的功能包，装来直接用）。给它两样东西：规则清单 + 一次请求，它回答 yes/no。
> 类比：它不是保安，是**门口刷卡的机器**——你录卡和清单，比对逻辑它包了。

模型核心（`auth/casbin.ts` 的 `RBAC_MODEL_TEXT`，matcher 一行）：

```
g(r.sub, p.sub) && keyMatch(r.obj, p.obj) && (r.act == p.act || p.act == "*")
```

翻成人话：**角色能对上（或继承自它）且 门牌对得上 且 动作相同或规则是万能钥匙** → 放行。

三个"不报错但静默失效"的坑：少了 `g(...)` 角色继承失效；少了 `keyMatch` 通配授权（`route:*`）失效；`'*'` 拼成 `':*'` 万能钥匙变废铁。

**适配器（Adapter）**：Casbin 不存数据，要有人把 MySQL 的 4 张表翻译成规则清单——这就是适配器，我们写成**只读**（写权限必须走管理接口，避免两条路改数据对不上账）。

**缓存与 TTL**：每请求查 2 张表，1000 请求 = 2000 次查询；加 30 秒缓存 ≈ 2 次。**TTL**（Time To Live，存活时间）= 缓存的保质期。
> 类比：把权限清单拍照贴门口，30 秒重拍一次。但刚改完权限照片还是旧的 → 经典投诉"我刚被授权了怎么还是 403"。
> **解法**：写操作成功后主动撕照片（`invalidatePolicyCache()`）。实测日志：

```
PUT /roles/2/permissions → 200
{"event":"rbac.policy.invalidated","reason":"PUT /v1/roles/2/permissions"}
{"event":"rbac.policy.loaded","policy_rules":47}   ← 下次判定真的重读了库
```

### 第 4 步：在门口装闸机 —— 中间件 `requireAction`

**中间件（middleware）**：Node 的 Web 框架 Express 里，请求依次经过一串函数，每个函数可放行或拒绝。
> 类比：机场安检传送带——X 光、金属探测，任何一道拦下后面全不发生。

业务接口只加一个参数：

```ts
api.post('/admin/routes', requireAction('route:line', 'add'), 真正干活的函数)
```

三种结果：没登录 → **401**/20012（组员1 拦）；没权限 → **403**/20013「权限不足，禁止访问」（Casbin 拦）；有权限 → 200。

**fail-closed（失败即拒绝）**：策略库挂了 → 退回登录时的权限快照（同口径）；都拿不到 → 拒绝。
> 类比：门禁断电即锁死，不是断电即全开。

403 响应**不返回缺什么权限码**——那等于给攻击者画"还差哪步"的地图；缺失信息只进服务端 `rbac.denied` 日志。

### 第 5 步：9 个管理接口 —— 让人能改权限

管理员不会写 SQL，要有个网页能勾选。核心接口：角色增删改查、权限树、**给角色全量覆盖授权**（`PUT /v1/roles/:id/permissions`）、查自己的菜单/按钮。

**必须懂的三个设计**：

**① 事务（Transaction）**：把多条数据库操作打成一个包裹，**要么全成、要么全撤销**。
> 类比：银行转账 = 你的账户 -100 + 对方 +100，崩在中间必须整体回滚。
> 授权接口 = 先 DELETE 旧勾选再 INSERT 新勾选，不包事务的话崩在中间 = 角色权限凭空清空。

**② 校验（Validation）**：进门先验货，不信任别人传的数据。角色编码必须大写字母开头；权限 id 9999 在表里不存在 → 400 拒绝。没有校验，脏数据进库会让 Casbin 加载策略时整个翻车。

**③ 幂等（Idempotent）**：同一操作做一次和一百次结果一样。
> 类比：电梯按钮连按 5 下只来一趟（反例：音量键按 5 下加 5 格）。
> 写请求都带 `Idempotency-Key` 头（一个 **UUID**——随机生成、几乎不可能重复的字符串，2^122 种可能，全球 80 亿人每秒生成 10 亿个也要 10 万年才撞一次）。网络卡了用户连点 3 下"新建角色" → 只建 1 个。

**④ 自动补祖先**：权限树是父子结构（系统管理 10 → 角色管理 11 → 新增角色 101）。只勾 101 时后端自动补 10、11 存成 `["10","11","101"]`——否则前端渲染侧边栏时找不到父节点，**菜单整条消失**，用户以为授权失败。
> 类比：快递地址只写"3 栋 501"不写市、区，快递员找不到——补祖先就是把地址链自动补全。

**⑤ 超管（SUPER_ADMIN）权限不许改**：全系统只有超管有"改权限"的权限，他若把自己清空，就没人能救回来，只能手工改数据库。

### 第 6 步：三层验证

| 层 | 命令 | 内容 |
|---|---|---|
| 单元测试 | `npm run test:rbac` | 12 个用例，不连库 |
| 真实联调 e2e | `npm run e2e:rbac` | 起真服务+真库+真登录，8 段断言，末行 `ALL PASS` |
| 数据库体检 | `npm run db:check` | 只读检查 .env/表/种子齐不齐 |

**e2e**（end-to-end，端到端）= 像真人一样登录、点按钮、看结果。
> 类比：单元测试是实验室测发动机，e2e 是把车开上路跑一圈。

**npm**（Node Package Manager）= Node 世界的应用商店+装卸工；`npm run xxx` = 执行 package.json 里 scripts 段的"快捷方式"（如 `e2e:rbac` → `tsx src/api/rbacRouter.e2e.ts`）。**tsx** = 能直接运行 TypeScript 的翻译官。

## 四、一句话主线（背这个）

> **解决了 3 个问题，用了 3 招：**
> **权限没地方存** → 4 张表存成 47 行勾选记录；
> **判断散落在代码里** → Casbin 唯一判定入口，路由一行 `requireAction(模块:资源, 操作)`；
> **改完权限不生效** → 30 秒缓存撑性能 + 写操作后主动失效保实时。

## 五、三个"亲手做一遍就彻底懂"的实验

1. **热更新**：`node backend/scripts/demoAuthorization.mjs --hot-reload`——观察"补上权限立即 200、摘掉立即 403"，配合服务端日志 `invalidated → loaded`。验证：写钩子使 30s TTL 不是"必须等 30 秒"的借口。
2. **菜单 ≠ 按钮**：建一个只授菜单码 `11` 的角色，用它的账号调 `GET /v1/roles` → **403**。验证：看得到菜单 ≠ 能调数据接口（菜单只折算成 view）。
3. **动作粒度**：同一角色只给 `route:line:query` → `POST` 新增线路 403；补上 `route:line:add` → 200。验证：`p.act` 真的参与匹配，有权限不等于全能干。
