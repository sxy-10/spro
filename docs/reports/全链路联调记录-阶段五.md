## 2. 判定口径（先统一标准，避免把"正确"记成"错误"）

| 符号 | 含义 | 典型例子 |
|---|---|---|
| ✅ 通过 | 行为与设计一致 | 超管能进管理中台 |
| 🟡 正确拒绝 | **没看到 / 被拦 是设计如此，不是 bug** | 游客看不到「管理中台」入口、社管点角色管理被 403 |
| ❌ 缺陷 | 该有的功能没有，或数据是假的 | 探索页数据来自前端 mock，不走接口 |
| ⚠️ 阻塞 | 环境/依赖问题导致无法验证 | 依赖没装、服务没起、Redis 不可用 |

**这一节是答辩时最容易被追问的地方**：老师问"你们 403 是不是有 bug"，你要能立刻区分"该拒绝"和"真故障"。

## 7. 接口层验证（curl 兜底）

页面点不出来时用接口确认。**三个必踩的坑**：POST 必须带 `Idempotency-Key`；本机访问必须 `--noproxy 127.0.0.1`；部分写接口还需 HMAC 签名。

| 接口 | 命令要点 | 期望 | 实际 | 结论 |
|---|---|---|---|---|
| `GET /v1/health` | `curl --noproxy 127.0.0.1 http://127.0.0.1:3001/v1/health` | 200 + JSON | `{"code":0,"message":"ok",...}` | ✅ |
| `POST /v1/auth/login` | body 用 `mobile`（不是 `phone`）+ 头 `Idempotency-Key` | 200 + token | 短信登录 `/auth/login/sms` 200，返回 `token/refresh_token/user_id`；⚠️ **`Idempotency-Key` 少于 8 字符会被拦成 10001** | ✅ |
| `POST /v1/auth/sms/send` | `{mobile, scene?}` | 200 + `dev_code` | 返回 `dev_code`（开发环境直出） | ✅ |
| `GET /v1/users/me/permissions` | 带 `Authorization: Bearer {token}` | menus/buttons 与角色一致 | 游客 6 buttons；社管 31 buttons；超管全量 | ✅ |
| `GET /v1/roles` | 超管 token | 200 + 角色列表 | 4 个角色：TOURIST(#1) / AGENCY_ADMIN(#2) / SUPER_ADMIN(#3) / AGENCY_STAFF(#4) | ✅ |
| `GET /v1/roles` | 社管 token | 403 | **403 / 20013 权限不足，禁止访问** | ✅ |
| `PUT /v1/roles/2/permissions` | 超管 token + `{permission_ids:[...]}` | 200 | 200 ok；追加后社管 `GET /roles` 由 403 → **200**（Casbin 热更新生效） | ✅ |
| `POST /v1/seckill/1` | body `{date, people}` + `Idempotency-Key` | 202 + `req_id` | 202 `{"status":"queued","req_id":...}` | ✅ |
| `GET /v1/seckill/result/{reqId}` | 轮询 1s × 10 | 由 `pending` 转最终结果 | `{"status":"success","order_id":"2"}` | ✅ |
