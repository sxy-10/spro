# 前端性能审计

## 结论与测量边界

当前分支没有原始景点图片，浏览器首屏也不加载任何图片；性能基线因此以首次进入计划页为主。审计发现的主要可量化问题是六个页面组件被同步打入首屏 JS。已将它们改为按需加载，并保留默认计划页正常显示。

本次未能生成真正的 Lighthouse 报告：临时安装 Lighthouse CLI 时，npm registry 多次返回 `ECONNRESET`，缓存中的 CLI 又缺少依赖。`lh-before*.json` / `lh-after*.json` 记录的是 Edge Performance API 兜底数据，不是 Lighthouse 原始报告；其中 Speed Index 未测，TBT 是基于 long-task 的估算。要完成老师要求的 Lighthouse 六指标审计，需要在网络可用后重跑 Lighthouse。

## Top 5 瓶颈

| 排名 | 瓶颈及证据 | 处理 |
|---|---|---|
| 1 | `App.tsx` 同步导入六个 Screen；优化前生产入口 JS 为 266,429 B（浏览器传输 88,609 B），不论用户是否切页都会下载。 | 已给六个 Screen 加 `React.lazy` / `Suspense`，并按 React、HTTP 拆 vendor。默认计划页初始 JS 传输降为 84,999 B。 |
| 2 | `App.tsx` 仍同步引用 `mockData.ts` 中的行程、消息、探索和管理端默认数据；这部分数据仍会进入初始依赖图。 | 本轮保留，以免改变已有页面默认数据行为；可在下一轮按页面拆分 fixture。 |
| 3 | `/routes`、`/spots` 默认列表在无缓存时分别执行列表和 count 两条 SQL，且此前没有 Redis 读缓存。 | 已增加 120 秒热点列表缓存、启动预热和命中/未命中日志；默认第一页走缓存，筛选/分页仍走原查询。当前本机 Redis 未启动，缓存命中与预热未能实测。 |
| 4 | 全局 CSS 首屏整包加载，生产文件 30,670 B（gzip 6,880 B）；页面级样式尚未拆分。 | 未拆 CSS，避免扩大页面样式改造范围；体积已纳入后续复测观察项。 |
| 5 | 优化前没有可供比较的景点图片，探索页也没有图片请求，无法验证 WebP、srcset 或图片字节数的变化。 | 已生成 3 张本地占位图的 480/960/1440 WebP，并在探索图钉使用 lazy、srcset 和显式尺寸。首次打开探索页的 3 张 480w 图共传输 6,946 B。由于原项目为 0 张图，不能宣称这部分较旧照片节省了字节。 |
