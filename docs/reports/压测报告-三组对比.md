## 2. 测试方法

**统一参数**：并发 `-c 50`，持续 `-d 20`（4 组均为 20 秒，C 组例外说明见下）。

| 组 | 目标地址 | 目的 |
|---|---|---|
| A | `http://127.0.0.1:3001/v1/health` | 后端直连基线 |
| B | `http://127.0.0.1:8080/v1/health` | 经 Nginx 反代，**无限流** |
| C | `http://127.0.0.1:8088/v1/health` | 经 Nginx 反代，**限流 20r/s + burst 40** |
| D | `http://127.0.0.1:8080/v1/routes?page=1&size=3` | 带数据库的真实业务接口 |

> **为什么 A/B/C 打 `/v1/health`**：该接口在 `router.ts:81` 定义，仅返回 `{status:'ok'}`，不查库、不鉴权，是纯粹的"网关层"基线。用它才能把 Nginx 的开销单独隔离出来。
> **为什么 B 必须走 8080**：8080 是不带限流的 server 块。若 B 走 8088，测到的是限流效果，不是反代开销。

## 4. 数据分析

### 结论 1：反代没有造成可测量的性能损失

- RPS：A 5,527 → B 6,931（**B 反而高 25.4%**）
- 平均延迟：8.54ms → 13.11ms（**+4.57ms**）

**反代不可能真的提速**，这是本机 loopback 场景下的正常现象，原因有三：

1. **Nginx 的 IO 效率高于 Node**：高频短请求下，50 个并发 socket 的读写由 Nginx 的事件循环承担，Node 只需处理复用的少量 upstream 连接（配置了 `keepalive 64`）。
2. **`proxy_buffering` 默认开启**：Nginx 快速收完 upstream 响应并释放连接，Node 不必等待客户端慢速读取。
3. **Windows 测量抖动**：同一配置复测波动可达 ±15%（见复测表 4,845 / 5,477 / 6,041）。

**答辩表述建议**（不要吹"反代更快"）：
> "延迟增加 4.6ms，绝对值仍在 10ms 级；吞吐差异落在这台机器 ±15% 的测量噪声内。结论是：在本机 loopback 场景下，反代开销可忽略，主要成本是 4.6ms 的固定转发延迟。"

### 结论 2：限流参数精确生效，且可用公式预测

C 组放行数 **443**，理论值 = `20 r/s × 20s + burst 40 = 440`，误差 3 个来自计时边界。

5 秒探针的验证更精确：放行 **140** 个 = `20 × 5 + 40`，**完全吻合**。

> 这是漏桶算法（leaky bucket）的教科书级证据，答辩时可以直接说："放行数不是随机的，等于速率×时长+突发桶容量。"

### 结论 3：系统是双层限流，不是单层

D 组的 2,602 个 **429（不是 500）** 暴露了第二层：

| 层级 | 位置 | 规则 | 作用 |
|---|---|---|---|
| 网关层 | Nginx `limit_req` | 20 r/s + burst 40，按 IP | 挡洪水，保护后端与数据库 |
| 应用层 | `router.ts:82` | **120 次/分钟/IP** | 按业务限流，返回 429 |
| 敏感接口 | `router.ts:86/210/211` | 登录 10/min、短信 10/min、**手机号 3/min** | 防撞库、防短信轰炸 |

> `/v1/health`（`router.ts:81`）注册在全局限流中间件（`router.ts:82`）**之前**，所以 A/B/C 三组不受应用层限流影响 —— 这是"基线干净"的关键，也是代码阅读得出的结论，不是猜的。

**D 组的正确解读**：不是数据库扛不住，是**请求在进入数据库之前就被应用层挡掉了**。这证明纵深防御有效。

**注意**：D 组无法测出数据库真实上限。要测需要绕过 120/min 限额（伪造 XFF 或临时改限额），属于破坏性操作，未执行。

### 结论 4：B 组 100 个客户端错误，是 keep-alive 参数不匹配

- `server.ts:9` 只设了 `headersTimeout = 15000`，**没设 `keepAliveTimeout`**，Node 用默认 **5 秒**
- Nginx upstream keepalive 的空闲连接若被 Node 在 5 秒后关闭，Nginx 复用时会拿到死连接
- 表现：`errors=100`、`non2xx=0`（客户端侧连接重置，服务端未返回错误码）
- 占比 100 ÷ 138,595 = **0.07%**，不影响结论

**建议修复**（属组员1/3 代码范围，本次未改）：
```ts
server.keepAliveTimeout = 65_000;  // 必须大于 nginx keepalive_timeout(60s)
```
